Jobs and Schedules — partitions, Run history, the queue, wechart's own schedules and when they suspend, folder by folder

Task T504, asked for by R40.4 ("Draw new designs first"). It is drawn from what's built today:

  • Jobs (JobsPage, BuildPanel): two tabs, Pre-aggregations and Queries. It has a docked pane (T469) and the Cube and refresh-worker badges (AC-156). Each row says only what the current browser session started.
  • Schedules (SchedulesPage): every refresh key, read-only, with a note that scheduling from wechart "isn't available yet".
  • T371 already limits both to Super-Admins, and to read-write members for their own folders.
  • No approved design draws AC-145, AC-150, AC-151, AC-155 or AC-234 (the 2026-09-28 sync check, H2).

This design adds:

  • A rollup's partitions in the pane, each with its state and when Cube last built it, and Rebuild selected (AC-145).
  • Run history and a build's log, for the builds wechart starts: from Jobs, and from wechart's own schedules (AC-150).
  • The queue, with Cancel for a queued build (AC-151).
  • wechart's own schedules on Schedules: a cron and a time zone, with the next runs. Each schedule sets how many failed runs in a row suspend it, 3 unless changed, and offers Resume (AC-234, AC-155).
  • The refresh worker's status from xcube: the revision each worker serves, when it last ran, and each module's last error.
  • The Folder column and filter, and the scope note, on every tab and on Schedules (AC-297), and three audit events (AC-294).

Screen 1 shows Wren Writer, a read-write member of Sales / EMEA (group sales-emea-rw), on Jobs. She has a partitioned rollup open and two of its partitions selected. Screen 2 shows Ada Admin, a Super-Admin, making a wechart schedule on Schedules. Sign-in is on for both. States A–J follow the brief's order, and each names its criteria. State J reconciles designs 10 and 07.

What R41 leaves out: the refresh worker's build history comes in the next phase. So nothing here says a build Cube started on its own failed, how long it took against the average, or that a schedule started it, and no list of recent builds includes such builds. Built states and last-built times come from xcube's partitions route, and Building and Queued from its queue route, whoever started the build.

What doesn't change: the Queries tab (a member's own queries, R42.6); Data as of on tiles (R42.7); the refresh-key form in the model editor (AC-153, T159); and the audit trail's filters, table and inspector (design 08).

Rebuild selected sends one build request per selected partition, so only those are built.

B · Run history and a build's log, for the builds wechart starts (AC-150)

Every build started from Jobs or by a wechart schedule is recorded by wechart's API. The API follows the build to its end with no browser open, and records it even after Cube's own record, kept for 24 hours, has gone. Each pre-aggregation keeps its latest 100 records. One start is one record (Q6). Builds Cube's refresh worker starts on its own aren't listed: their history comes in the next phase (R41). Rows aren't counted, since Cube's jobs API reports none.

C · The queue, with Cancel (AC-151)

What xcube's queue route lists for the model, in the queue's order: every build waiting or running in your folders, whoever started it. Each entry shows its pre-aggregation, partition, state, who started it and its token. A queued build wechart started has Cancel. Cube's refresh worker queues a build it lost to a cancel again at its next run, every 30 seconds, until its refresh key turns over. So the worker's entries are drawn without Cancel, and so are those a query started (Q1). The tab updates while it's open.
