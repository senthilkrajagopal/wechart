# xcube v1.7.45-22132c309c: fresh connection health, and publishes that don't fail on a data source that's already gone (on Cube v1.7.45)

This doc is the sibling of [xmr] (`40efaef823`) and [x6]. It covers the four commits from `40efaef823` to `22132c309c`:
- `4660b5d806` and `8296c077e5`: wechart's golden sealing vectors, as an xcube test;
- `1e4c4aae02`: the connection-health heartbeat;
- `22132c309c`: the fix for the race between a publish and a connection's removal.

It checks xcube's three answers ([ans-gv], [ans-hb], [ans-race]) against wechart's asks ([req-gv], [req-hb], [req-race]). It says what T364/T365, T436, T437 and T456 need, and corrects [xmr] and [x6].

**Headline findings**
1. **Pin `22132c309c`.**
   - Its image carries everything in `40efaef823`'s ([xmr]), plus the heartbeat and the race fix ([cmp]).
   - `1e4c4aae02`'s image has the heartbeat but not the race fix ([reflog] L20-21).
   - wechart still pins `ed08180c37` ([w-compose] L165, L200).
2. **The heartbeat.**
   - Every `XCUBE_CONNECTION_HEARTBEAT_MS` (default 600000; 10000 to 1800000 allowed), each process re-writes its report of each connection it holds a live driver for. It keeps version, state and error; only `reported_at` moves ([set] L107-115, L178; [conn] L298-330; [rev] L690-698).
   - wechart's `cubeStateOf` needs no logic change ([w-state] L28-43).
3. **The race wechart reported went through xcube's dry run, not the applied changeset.**
   - The body wechart saw is wechart's own 422 from `checkWithXcube` ([w-pub] L241-294; [w-e2e] L174-180).
   - At `22132c309c` a failed dry run is checked once more against the new head, and answers 200 ([rt] L2987-2990).
   - The applied changeset answers `409 conflict`, which wechart's `modelSync.apply` already re-reads and sends again ([w-client] L380-385; [w-sync] L183-211).
4. **New limits, found by reading:**
   - Reports are per connection per process, not per driver (Gotcha 2).
   - Another instance's heartbeat can re-create a removed connection's row (Gotcha 6).
   - A `409 conflict` can now name the same revision the client sent (Gotcha 12).

## API surface we will use

All model routes are `{CUBE_API_URL}/v1/semantic/models/{model}/…` ([routes] L287). Errors are `{ error, code, …details }` ([routes] L294-296).

### `GET …/connections/{name}/health`: same shape, fresher `reportedAt`

- **The shape is unchanged:** `{ model, name, version, revisions, instances: [{ instance, version, state, error, reportedAt, current }] }`, with `current = (report.version === stored version)` ([routes] L585-592; [rt] L1841-1854).
- **One row per model, connection and process.** The key is `(model, name, instance)` ([mig] L217-226). The instance is `${hostname}/${pid}/${6 hex}` ([rt] L412).
- **`reported_at` is the xcube database's `now()`** at each write ([rev] L690-698).
- **Rows are removed only by the connection's `DELETE`** ([rev] L683-684). That is the only statement deleting from `connection_reports` (Grep of `src`).

**When a process writes its row at `22132c309c`:**

| Event in the process | Row written | Kept fresh by the heartbeat? | Source |
| --- | --- | --- | --- |
| First use: a driver is built and tested | `live`, the stored version | Yes, while that driver is live | [conn] L352-381, L320-330 |
| First use fails (build, or `testConnection` within 30 s) | `failed`, the stored version, redacted error | No. Dropped at the next tick, so the row ages out, **unless the process holds another live driver for the same connection** (Gotcha 2) | [conn] L333-346, L357-364, L322-327 |
| A changed connection swaps in | `live`, the new version | Yes | [conn] L436-447 |

**The heartbeat itself:**
- **Timer.** `setInterval(connections.heartbeat, connectionHeartbeatMs ?? 600000)`, `unref`'d. It is set at the end of `start()` and cleared in `stop()`. A failure logs `xcube: could not report connections` ([rt] L604-612, L615-625). The first tick comes one interval after start, but a build reports at once ([conn] L380).
- **What a tick writes.**
  - For each key in `lastReports` with a non-removed live entry, it calls `writeReport(key)`. That upserts `lastReports`' `version`, `state` and `error` as they stand, with `reported_at = now()` ([conn] L320-330, L298-303; [rev] L690-698).
  - Keys with no such entry are deleted from `lastReports`, and nothing is written ([conn] L325-327).
- **Queueing against swap reports.**
  - `report()` sets `lastReports` first, then queues a write ([conn] L287-291).
  - Writes chain per `<model>/<name>`. Each reads `lastReports` when it runs, not when it was queued ([conn] L298-312).
  - So a heartbeat queued before a swap's report can't write the older state after it. A write failure is logged `xcube: could not report a connection` ([conn] L304).
- **Tests.**
  - [t-conn] L257-264, "an instance re-reports the connections it holds, keeping what it reported, so a report within the hour means running". It calls `heartbeat()` directly. It asserts that `reportedAt` rose, and that `instance`, `version`, `state: 'live'` and `current: true` are unchanged.

  - [t-admin] L151-176: default 600000; `3600000` and `100` refused.
  - **Not tested:** the timer wiring, `failed` rows kept or dropped, a heartbeat racing a swap, several drivers per connection, several processes.

### `POST …/changesets` and `PUT …/snapshot` (items): when `409 conflict` answers now

The answer is unchanged: `409 { error: "The model changed since the <changeset|snapshot>'s base revision", code: 'conflict', currentRevision, currentItemsHash }` ([routes] L218-226, L294-296, L364-368, L521-526). It now has three causes:

1. **A stale base.** This is as before: the base isn't the head, and the items aren't already the head's ([rt] L3027, L3035-3038).
2. **A check that fails while the model moved on.** `validateModules` fails, and `movedSince(model, head)` finds another revision than the one read at the start ([rt] L3081-3086, L2994-2997).
3. **A changed cube's connection is gone at commit.**
   - `importItems` receives `dataSources = boundConnections(changed items)`: every changed cube's bound data source except the root `default` ([rt] L2879-2889, L3104-3105).
   - It is passed only when the model has connections ([rt] L1795-1800, L2985).
   - Under the model row lock, `write()` refuses unless all of them still exist in `connections` ([rev] L873-882, L903-911).
   - Here `currentRevision` is the head just locked, which can equal the base the client sent ([rev] L909-910; [routes] L224).

**How the race resolves.**
- The check compiles the items of the head it read ([rt] L2975-2986). Cube's `driverFactory` then asks `connections.of(model)`, which is re-read after a change. A model with connections refuses any non-`default` name it doesn't hold: `Data source "<n>" of model "<m>" has no connection` ([cfg] L185-205; [conn] L151-166, L424-426).
- Case 2 turns that refusal into a conflict when the head moved meanwhile.
- **Tested** ([t-conn] L374-408, "a publish checked while another folder's data source goes is told its base moved, never refused over it"):
  - The hook `beforeValidate` runs the other writer as the check begins ([t-conn] L50-66). That writer deletes `fa/sales`, then `DELETE`s `fa__warehouse`.
  - The publish then answers `409` `{ code: 'conflict', currentRevision: <the other writer's> }` (L404-406).

### `POST …/changesets?dryRun=true`: one more check

- When the first check is not valid and the head moved since it was read, `applyChangeset` runs again once (`again = true`), against the new head. It answers as that second check does ([rt] L2963-2992).
- It never answers `409 conflict`. The conflict branch is `!check` only ([rt] L3035-3045). The route answers the check's body with 200, and uses `answerItems` only for `mode` ([routes] L502-516).

### `DELETE …/connections/{name}`: taken at the revision it checked

- Up to 5 tries ([rt] L1816-1838):
  1. read the head;
  2. list the cubes bound to the name at that head ([rt] L1802-1814). Any user gives `409 in_use`, as before;
  3. `store.deleteConnection(model, name, head.revision)`.
- The store sets `lock_timeout = '10s'` and runs `SELECT current_rev … FOR UPDATE` on the model row, the lock a publish's `write()` takes ([rev] L675-682, L873-882). Then:
  - if `current_rev` ≠ the revision checked, it answers `'moved'` and the runtime tries again;
  - otherwise it deletes the connection and its reports, and notifies (L683-686).
- **After 5 tries it gives up.** It throws `unavailable('Model "<m>" kept changing while connection "<n>" was removed; try again')`, a `CubejsHandlerError(503)` ([rt] L334-336, L1837). The route answers that as `503 { error, code: 'unavailable' }` with no `Retry-After` ([routes] L328-330).
- Otherwise it answers `204`, whether or not the connection existed ([routes] L595-601).
- **Tested** ([t-conn] L410-420, "a publish binding to a data source removed after its check is not stored; a removal waits out a publish"). The test calls the store directly:
  - `importItems` with `dataSources: ['fa__gone']` answers `conflict`, and the head doesn't move;
  - `deleteConnection(…, head − 1)` answers `'moved'`.
  - That a removal waits on the lock is by reading only (Gotcha 17).

## Gotchas

**The heartbeat**

1. **A bad `XCUBE_CONNECTION_HEARTBEAT_MS` stops both Cube processes at start** (exit 1). Values out of range, non-integers and negatives all do this ([set] L95-115; [bin] L52-55).
2. **One row per connection per process, and the last event wins.**
   - A process holds one live entry per driver Cube asks for. `resolveDriver` calls `driverFor` for every orchestrator, including preview orchestrators and pre-aggregation drivers ([srv] L80-98; [conn] L379).
   - `lastReports` keeps one state per `<model>/<name>` ([conn] L136-137, L287-290).
   - **A first-build failure on one driver is kept fresh while another driver serves.** The heartbeat checks only that some entry is live ([conn] L323). Nothing retries a first build that failed: `refresh()` only revisits entries ([conn] L476-481). So the row stays `failed` and current, and wechart shows "Cube couldn't take these settings", until the process reports again for that connection. By reading.
   - **The reverse is possible too.** One entry swaps (`live`) after another failed (`failed`), so `live` is written last. The poll's `refresh()` re-tries the failed entry within `XCUBE_POLL_INTERVAL_MS` (60 s by default) and reports `failed` again ([conn] L424-457, L464-481; [set] L166).
3. **A failed first build shows `failed` and `current: true` for up to an hour, then disappears** (unless Gotcha 2 applies). The next query builds again and reports again ([readme] L748-749; [conn] L357-364).
4. **A failed swap stays `failed`, `current: true` and fresh while the old driver serves.** The poll re-tries it ([conn] L448-453, L464-481). wechart's `failed` state is right for it ([w-state] L38).
5. **Rows are never deleted except by the connection's `DELETE`.** A stopped process's row stays in the answer with an old `reportedAt`, so keep filtering by the hour ([rev] L683-684; [w-state] L32-34).
6. **Another instance can bring a removed connection's row back.**
   - `connection_reports` has no foreign key ([mig] L217-226), and `reportConnection` is an unconditional upsert ([rev] L690-698).
   - A process whose heartbeat (or build report) lands after another instance's `DELETE` commits, but before it hears the notification, writes a row again ([conn] L320-330; [rt] L2130-2134).
   - The row is invisible while the name is absent, because health answers 404 ([rt] L1843-1846).
   - If the name is pushed again, the row shows `current: false` until that process reports again or the hour passes.
   - By reading. The test is one process, run in sequence ([t-conn] L306-317).
7. **`reportedAt` is xcube's database clock, and wechart compares it with the API host's clock** ([rev] L693-695; [w-route] L260). Skew moves the hour's edge.
8. **Health doesn't show old drivers still draining.** After a swap, calls in flight finish on the old driver for up to 30 min ([x6] "Applying it").
9. **A process that can't write reports drops out after an hour.** Each failure is only logged ([conn] L304). It then no longer counts toward "every instance".
10. **The heartbeat's tests call `heartbeat()` directly.** They cover only `live` and removal, in one process (API surface).

**The race fix**

11. **The dry run is checked again only once.** A second removal racing the second check still answers `valid: false`, naming a data source the change doesn't use. wechart then answers 422 ([rt] L2987-2990; [w-pub] L294).
12. **`409 conflict` now has three causes, and `currentRevision` can equal the base sent** (API surface). wechart's apply loop ignores `currentRevision` and re-reads ([w-sync] L183-192).
13. **Under steady writes, a changeset that really fails can answer `409`, not `422`.** Case 2 answers `409` whatever the failure was ([rt] L3081-3086). wechart's apply then ends `failed` ("kept changing") after 4 sends, without the errors ([w-sync] L212-213). By reading.
14. **What the commit-time check covers.** It checks only the connections of changed cubes, other than the root `default` ([rt] L2879-2889). Unchanged cubes are covered by `DELETE`'s `in_use` check at a locked revision. The root `default` falls back to Cube's environment by design ([x6] Gotcha 6).
15. **A resent publish binds afresh.** It binds to a farther data source of the same name, or answers `422` "… which no folder on this item's path holds" ([ans-race] L23; [x6] "Binding at publish"). wechart's apply loop re-sends with no new check ([w-sync] L183-211).
16. **`DELETE …/connections/{name}` can now wait, and fail in two new ways:**
    - It takes the model lock with `lock_timeout 10s` ([rev] L677-679).
    - A lock timeout (SQLSTATE 55P03) matches none of the `unavailable` patterns, so by reading it answers `500 internal` ([routes] L331-335; [x2] Gotcha 17).
    - After 5 moved tries it answers `503` with no `Retry-After` ([routes] L328-330).
17. **The store-level test calls the store directly.** It exercises the `'moved'` answer, not a removal actually blocking on a publish ([t-conn] L410-420).

**The rest**

18. **wechart's development credential key is now in two public places.**
    - xcube's public fork holds it as a fixture ([fx] L6-8; [a-4660]), as does wechart's repo ([w-infra] Glob: `infra/xcube/dev-credential-key.pem`).
    - Compose seals to its kid ([w-compose] L37). Anyone can open a secret entered in local compose.
    - Helm uses a key its Job makes ([w-helm-cube] L98-106).
19. **When wechart changes `golden-v1.json`, xcube's copy must be refreshed** ([ans-gv] L16; [fx] L10).
