## Summary for wechart

- **Names are bare everywhere.** A cube, view or data source is served, stored and addressed under its own name in every folder. There is no `<folderId>__` prefix anywhere ([answer, "1.1"]; [items] L59-66, L265-270; [pub] L555).
- **Two namespaces, each unique model-wide, compared in any case.** Cubes and views share one; data sources have their own ([answer, "2.1"]; [items] L37-40, L78-81).
- **First to land wins.** xcube refuses a second item of a name with `422 invalid_items` kind `name_in_use`, and a second data source with `409 name_in_use`. Neither refusal names or hints at the other item's folder ([answer, "The error kinds"]; [pub] L299-302).
- **No nearest-first resolution.** A name means the one item of that name, matched exactly ([answer, "3.1"]; [rw] L16-33).
- **Every reference stays on the referrer's folder path (R72).** So does every cube's data source, inherited ones too ([answer, "4", "R72"]; [pub] L330-390).
- **The connection PUT needs `baseVersion`.** `null` creates; a number edits or moves that version ([answer, "2.5"]; [routes] L172-178).

### Two namespaces, compared in any case

- **Cubes and views share one namespace; data sources have another.** A cube and a data source may share a name ([answer, "2.1"]; [asks] 2.1).
  - Cube keeps cubes and views in one map, and a second item of a name silently replaces the first. So xcube's check is the only guard ([grammar, "2.1"], citing Cube's `CubeSymbols.ts:328`).
- **Names compare in any case.** `nameKey(name)` is `name.toLowerCase()`, and an item's identity, `itemKey`, is its `nameKey` ([items] L37-40, L78-81).
- **Split views count.** A view whose `cubes` entry has `split: true` makes Cube add a view named `<view>_<alias or last join_path segment>`. xcube counts those names: `checkNames` refuses a split name already in use, and an item whose name a kept view's split already takes ([pub] L286-328; [t-names] L276 "a view's split views take names too").
- **References match exactly; only uniqueness ignores case.** `Scope` maps each item by its exact name, as Cube's `resolveSymbol` does. So `{amount}` stays a member when the model holds a cube `Amount` ([rw] L16-33; [answer, "3.1"]).

### The grammar

| Rule | Exact value | Source |
| --- | --- | --- |
| Pattern | `^[A-Za-z][A-Za-z0-9]*(?:_[A-Za-z0-9]+)*$`: a letter, then letters, digits and single underscores, not ending in one. So never `__`, a leading `_` or a trailing `_` | [items] L12-19 |
| Length | At most 40 | [items] L21, L83-89 |
| Message | `"<x>" is not a valid name: a letter, then letters, digits and single underscores, not ending in one, at most 40 characters` (for a data source: `… valid data source name: …`) | [items] L83-89 |
| Reserved, compared in any case | Python's keywords `and as assert async await break class continue def del elif else except finally for from global if import in is lambda nonlocal not or pass raise return try while with yield`, plus `None True False`; Cube's names `CUBE TABLE SECURITY_CONTEXT securityContext FILTER_PARAMS FILTER_GROUP SQL_UTILS USER_CONTEXT COMPILE_CONTEXT`. The set holds them in lower case (`security_context`, `securitycontext`, …), 44 entries in all | [items] L23-35, L91-100 |
| Reserved message | `"<name>" is a reserved word and can't be a name` | [items] L96-98 |
| Data sources | The same pattern and length, **without** the reserved words (`table` is a valid data-source name) | [items] L102-105; [answer, "2.2"] |
| `default` | The root's alone, and only in lower case (see "`default`" below) | [rt] L1879-1892 |

- **Why these limits** ([grammar, "2.2"]):
  - `__` and a trailing `_` are out because Cube names a member's SQL column `<cube>__<member>`.
  - The reserved words are out because Cube's YAML compiler reads `{…}` as Python, and Cube resolves its own names before any cube's.
  - 40 is xcube's own limit, kept.
- **An upper-case name is quoted in Cube's SQL API** (`SELECT … FROM "OrderItems"`), as Postgres folds unquoted names. wechart queries through `/v1/load`, where this doesn't arise ([grammar, "2.2"]).
- **The connection route's `{name}`** is checked with the data-source grammar. A bad one is `400 invalid_connection_name`, with the grammar message as `error` ([routes] L655-661).

### On `DELETE …/connections/{name}`

- **`409 in_use`** names the cubes by bare name: `{ error: "Connection \"warehouse\" is used by what is published", code: "in_use", problems: ["orders uses it"] }`. Twenty at most are named, then `, and <n> more` ([rt] L2010-2019).
- **Who counts as a user:** a published cube whose own `data_source` is that name, or, for `default`, a cube naming none and extending none ([rt] L1992-2003; `src/overlays/connections.ts` L10-16). A child that inherits the data source through `extends` isn't listed, but its parent is, so the delete is still refused.

### On `PUT …/folders`

- **`409 data_source_range` or `409 reference_range`**, `{ error, code, cubes, items }`, by name ([routes] L376-379; [rt] L3618-3647):

  - `cubes`: cubes whose data source would leave their range; `items`: items whose references would;
  - `code` is `data_source_range` when `cubes` isn't empty, else `reference_range`;
  - only what the new tree strands counts, not what was already out of range ([rt] L3634-3637).
  - Tests: [t-conn] L446-447 (`{ code: "data_source_range", cubes: ["deep"], items: [] }`); [t-items] L341 "a folder push that would strand a reference is refused, naming the referrer (R72)".

### Which messages name a folder

- **No refusal names or hints at another item's folder** ([answer, "The error kinds"]). The source agrees: `inUse`, `checkRanges` and `checkReferences` build their messages from names alone ([pub] L299-302, L348-353, L380-386). - **Every `errors[]` entry carries `folderId`,** which is the caller's item's own folder ([pub] L300-301, L349-350, L381-382).

## Concurrency and identity

### First to land wins (2.4)

- **Publishes** land under the model's row lock (`SELECT … FROM models WHERE id = $1 FOR UPDATE`), on their base revision ([rev] L964).
  - Two racing for one name: one lands; the other gets `409 conflict` (stale base); its retry on the new base gets `422 name_in_use` ([answer, "2.4"]; [t-items] L325-339 "two publishes racing for one new name: the first to land wins, the other is refused on its retry (R71 2.4)").
- **Connection PUTs** run their checks inside the same lock, as a guard before the upsert ([rev] L694-723; [rt] L1915-1962).
  - Migration 14 adds a unique index on `connections (model, lower(name))` besides ([mig] L379-380).
  - Two creates racing for `racer` and `Racer`: one `200`, one `409 name_in_use`, and one data source is left ([t-conn] L402-410).
- **A publish is stored only while what it was checked against holds** (the publish `basis`) ([rev] L59-73, L987-998):
  - the model's data sources, by name and folder;
  - for a changeset, the folder tree.

  Otherwise the store answers `conflict`, which the route answers as `409 conflict` with `currentRevision` and `currentItemsHash` ([routes] L270-274). So a connection PUT or folder push between a publish's check and its landing can't slip a stranded cube in ([answer, "2.4"]; [t-conn] L493 "a publish checked against data sources or a tree since changed is not stored; …").

### A connection PUT says create or edit (2.5)

- **`baseVersion` is required** ([routes] L172-178):
  - `null` creates the data source. It is refused (`409 name_in_use`) while any data source holds the name, in any case. **A create never overwrites** ([rt] L1928-1934).
  - A number edits that version: in place, or moved to the body's `folderId` ([rt] L1935-1962).
- **`GET …/connections`** gives each data source's `version` (with `name, folderId, driver, authMethod, fields, secrets, revisions, updatedAt`) ([rt] L1967-1983).
- **The PUT's `200`** answers `{ model, …connection }`, its new `version` included ([routes] L677-684; [rt] L1964-1979).

### Overlays: an item is its name (2.6)

- **An overlay upsert stands in for the published item of its name, wherever either is,** for that overlay only. No `name_in_use` is raised for an overlay against published items ([pub] L70-75, L456-458; [t-names] L454 "an overlay item with a published item's name is its edit, wherever either is (2.6)").
  - A use-only copy in another folder, carrying a measure of its own, previews; the published model doesn't serve that measure ([t-ovl] L266-284).
- **Two upserts of one name in one overlay** are refused, in any case (`name_in_use`) ([pub] L431-440; [t-names] L480).
- **Overlay connections** ([rt] L1736-1777, L1565-1589):
  - one with a published data source's name stands in for it;
  - two of one name, in any case, are `409 name_in_use`: `The overlay brings two data sources named "<n>"; names are one per model`;
  - `default` is the root's alone: `400 default_outside_root` ([t-conn] L414-421).
- **A new name landed elsewhere since the push** isn't refused at the push. It is refused when it lands ([answer, "2.6"]).
- **The push checks only the overlay's own items** for R72 and the data-source rule ([pub] L530-536). See "R72" below.

### A move inside one changeset (2.7)

- **A changeset deleting `A/orders` and upserting `B/orders` is a move.** The item lands in B, and what refers to it is untouched ([pub] L445-466; [t-items] L312-323: a view over `orders` keeps `bindings: { orders: 'orders' }` and still answers).
- **Without the delete,** the upsert is `name_in_use` ([answer, "2.7"]).
- **An items snapshot** that moves an item is the same: it resolves every item afresh, keyed by name ([pub] L446; [answer, "2.7"]).

## What stays, and what was removed (3.3, 3.4)

- **`bindings`** are still reported, as `{ name: name }`: the items an item refers to, as written ([rw] L92-98; [answer, "3.3"]). Modules still form groups by union-find over them ([answer, "1.3"]).
- **`dataSource` and `extends`** stay in `GET …/items` and in every items answer ([answer, "3.3"]; [readme] L1400-1410; [t-items] L205-212).
- **`POST …/resolve` stays.** `{ folderId, names, overlay? }` answers `{ model, revision, folderId, overlay?, names: { <asked>: <stored name> | null } }` ([rt] L3981-4016; [routes] L159-163, L637-640):

  - with `overlay`, the overlay's upserts stand in first, and its deletes take published items out ([rt] L3995-4007; [t-ovl] L268-271);

## The data-source rule (4.1 to 4.4)

- **4.1.** A cube may use a data source only in its own folder or an ancestor ([pub] L330-358).
- **4.2.** `default` is the root's alone.
  - A `default` outside the root, or not in lower case, is `400 default_outside_root`, on the connection route and in an overlay ([rt] L1879-1892, L1750; [t-conn] L414-421).
  - A cube naming no data source uses the root's `default`. One that `extends` inherits its parent's ([pub] L106-122).
- **4.3. Where it is checked:**
  - at every publish (snapshot, changeset, approval), for every cube, published ones too ([pub] L529-536);
  - at `PUT …/folders`, under the model's lock ([rt] L3624-3644);
  - on a connection move ([rt] L1949-1961);
  - at an overlay push, for its own items and connections ([pub] L530-531; [rt] L1565-1589).

  The refusal names the cubes, never the data source's folder ([answer, "4.3"]). Test: [t-conn] L424 "a cube is refused a data source off its path: at publish, overlay push, connection move and folder push (R71 4.3)".
- **4.4. An inherited data source is held to the rule,** however far up `extends` goes, as wechart's user chose ([choices] "4.4"; [pub] L111-122).
  - The refusal names the parent: `(through w, which it extends)` ([pub] L348).
  - With R72 it rarely fires alone. `extends` must point up the path, and the parent's data source is in the parent's range, which lies inside the child's ([answer, "4.4"]).
- **A cube naming a data source the model doesn't hold** is kind `reference`: `It uses the data source "<x>", which the model doesn't hold` ([pub] L392-407). The range check leaves it to that refusal ([pub] L330-333).

## R72: every reference up the referrer's folder path

- **Kind `reference_range`.** It covers what an item's `bindings` record ([pub] L360-390):
  - a join;
  - `extends`;
  - each segment of a view's `join_path`;
  - `{cube.member}`;
  - `FILTER_PARAMS.<cube>`;
  - any other transpiled field naming a cube, such as a pre-aggregation's `rollups` ([readme] L218-224).

  A self-reference is ignored ([pub] L378).
- **Where it is checked:**
  - **at every publish,** for every item, published ones too: a move in a changeset can strand a published referrer, which is then named ([pub] L529-533; [t-names] L347);
  - **at `PUT …/folders`:** `409 reference_range` with `items` ([rt] L3634-3644);
  - **at an overlay push,** for the overlay's own items only ([pub] L530-531);
  - **not on a connection move,** which moves no item ([rt] L1949-1961 checks only `cubes`).
- **Tests:** [t-names] L313-347 (sibling-branch join, view, `extends`, `{cube.member}` and `FILTER_PARAMS`, the same up the path allowed, a move that strands a referrer); [t-items] L278, L341.
- **Settled by the coordinator (2026-10-07): the overlay push keeps checking only its own items, as built** ([answer, "Settled since"]).

## Aliases and rollup tables (1.2)

- **xcube writes a `sql_alias` only where Cube's own would go wrong** ([pub] L165-188):
  - **a name with upper case:** its lower-case form, since Cube snake-cases names (`OrderItems` and `order_items` would both be `order_items`; `ORDERS` would be `o_r_d_e_r_s`);
  - **a cube on a data source other than Cube's default,** its own or inherited: `<name>_<hash4>`, or `x<hash7>` when that is longer than 20 ([pub] L47-58), as from e53cf2a8b8;
  - **a cube that extends another:** an alias of its own, or Cube would give it its parent's ([pub] L173-174, L186);
  - **a name whose rollup table stem** (`<alias>_<pre-aggregation>`, at most 25) **or a member's alias** (`<alias>__<member>`, at most 63, plus 8 for a time dimension) **would be too long:** `x<hash7>` ([pub] L157-163, L183-185).
- **A pre-aggregation whose stem is still too long** gets `p<hash6>`, unless it has indexes ([pub] L246-255).
- **An authored `sql_alias` is kept** ([pub] L200).
- **Unchanged:** connection-identity aliases (`xcube-bc18f82c01.md`) are applied on top, at serving: `x<hash of name@<data source>@<identity>>` for a cube on a connection moved from its base ([ali] L105-115, L174-230; [answer, "1.2"]).
- **xcube no longer writes `title`.** `finish` adds only `meta.xcube` ([pub] L220-224). Cube's own title from the name is the same text. An authored `title` is kept as written ([answer, "1.2"]).
- **Every table and column name fits 63 bytes on Postgres, for every resolved item.** Before, only folder items were checked ([answer, "1.2"]; [pub] L232-284 check `resolved` entries in any folder).
- **`alias` refusals that can still fire** ([pub] L232-284; [answer, "1.2"]):
  - a pre-aggregation with indexes whose name is longer than 16 characters (25, less the hash alias's 9): `Pre-aggregation <pa>'s rollup table name would be too long: shorten its name to at most <n> characters`;
  - a member whose snake-cased name passes 53 characters (45 for a time dimension): `Member <m>'s SQL alias would be longer than 63 characters; shorten the name`;
  - two cubes with one SQL alias (`Its SQL alias "<a>" is also <name>'s`), or two pre-aggregations making one table (`Pre-aggregation <pa> would share its table <t> with <owner>`).
- **R72's last smaller call.** Whether a non-root item keeps a short `sql_alias` now follows the rule above. A plain lower-case cube on `default` with short names gets no alias in any folder: `generatedAlias` returns none when the alias equals the name and nothing calls for its own ([pub] L186-187; [t-names] L90 "items keep their names in every folder; xcube adds only where they came from").

## Deleted names (5.1, 5.2)

- **5.1. Paths that changed a landed name in place are now refused:**
  - a changeset upserting a landed item in another case (`name_in_use`, "in use as") ([pub] L459-461);
  - a connection PUT naming a data source in another case (`409 name_in_use`) ([rt] L1936-1938).
- **An items snapshot** sending `Orders` and not `orders` is a delete and a new item. Anything referring to `orders` refuses it ([answer, "5.1"]; [pub] L446 keeps nothing on `replaceAll`, L487-505).
- **An alias change never changes a name** ([answer, "5.1"]).
- **5.2. A new item reusing a deleted item's name** ([answer, "5.2"]):
  - it gets the same alias only on the same data source, with the same connection identity (the identity alias keys on the identity, [ali] L174-230);
  - connection bases outlive their connection, so a data source deleted and created again elsewhere is served under another alias;
  - Cube reuses a cached result only for identical SQL over the same identity, and a rollup table only when the pre-aggregation's SQL and structure hash the same, as Cube versions table names by both.
  - **So the new item is never served the old definition's results.** That last step is xcube's reasoning about Cube's keys, UNVERIFIED by wechart beyond [t-conn] L622 "a cube published again onto another data source answers from it at once, never from the old one's cache".
  - **T707 needs no wechart behaviour for 5.2.**

## Old schemas (6.1 to 6.3)

- **6.1. No migration of prefixed items** ([answer, "6.1"]).
- **6.2. Schema version 14** ([mig] L361-382):
  - **It refuses to start on a schema holding any folder-prefixed name:** an item whose `full_name` isn't its `name`, or a data source or connection base whose name holds `__`.
  - **The message:** `xcube: this schema holds folder-prefixed names, from before names were one per model; this xcube serves bare names only: drop the schema and seed it again`.
  - **Nothing of 14 is applied,** so the schema stays at 13. Each migration runs in its own transaction and is rolled back on error ([migrate] L116-128; [t-store] L96-99).
  - **A schema holding only root items and the root's data sources migrates** ([t-store] L103-105).
  - **`minReader` is 14,** so an older image refuses the migrated schema at start: `xcube: schema <schema> needs xcube schema version 14 or later to read it; this is 13` ([mig] L367; [migrate] L95-100; [t-store] L105-107).

- **6.3. Dropping xcube's schema is enough for correctness,** by 5.2's reasoning ([answer, "6.3"]). For tidiness, also clear:
  - the model's pre-aggregation schema (`<schema>_<model>_<hash>`);
