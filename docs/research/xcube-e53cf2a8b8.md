# xcube v1.7.45-e53cf2a8b8: a rebound cube is another SQL alias, and `GET …/items` names each cube's data source (on Cube v1.7.45)

This doc is the sibling of [x22] (`22132c309c`), [x6] and [xmr]. It covers the one commit from `22132c309c` to `e53cf2a8b8` ([cmp]). It checks xcube's answer ([ans]) against wechart's two asks ([req-cache], [req-items]), and says what T459 (AC-157), AC-273 and AC-161 need. It also corrects [x22], [x6], [xmr] and [x3a] where they no longer hold.

**Headline findings**
1. **The image to pin is `e53cf2a8b8`** (the user pins).
   - It is `22132c309c` plus this one commit ([cmp]: ahead by 1, behind by 0; [a-e53] parent `22132c309c…`).
   - wechart still pins `ed08180c37` ([w-compose] L165, L200).
2. **`GET …/items` now gives every cube a `dataSource`.**
   - The value is a string or `null`. Views have no such key. Nothing else in the answer changed ([rt] L3225, L2891-2899).
   - T459 can map each string to a wechart data source by exact name with `connectionNameOf` ([w-conn] L111-113).
   - `null` (a cube that `extends` another) can't be resolved from this answer alone. It can be resolved using wechart's own `extends:` value and the child's `bindings` (API surface).
3. **A cube bound to anything other than the literal `default` gets an SQL alias that names that data source** ([pub] L57-67, L118-133).
   - For wechart's folder cubes, whose full names are always longer than 20 characters ([w-folders] L8-14, L22-25), the alias is `x` plus 7 base32 characters of SHA-256(`<fullName>@<dataSource>`).
   - A rebind therefore produces new SQL, new result-cache keys and new rollup table names ([c-qc] L469-481; [c-bq] L4229-4246, L4393-4396).
4. **Limits found by reading:**
   - **`extends` children.** xcube's advice to "publish the child again too" doesn't change a child's alias (Gotcha 2).
   - **Root children.** A root child without an alias takes its parent's alias through Cube's prototype (Gotcha 3).
   - **Authored aliases** are not protected (Gotcha 4).
   - **Connections changed in place** are not protected (Gotcha 5).
   - **Short root names** carry only a 20-bit hash (Gotcha 9).
5. **xcube's test doesn't run the cache mode it names.**
   - It puts `cacheMode: 'stale-while-revalidate'` inside the query, and Cube overwrites that with `stale-if-slow` ([u-q] `normalizeQueryCacheMode`; [u-gw] `GET /v1/load`).
   - The fix itself doesn't depend on the mode. The key is the SQL.
6. **Upgrading from `ed08180c37` rebuilds nothing at start.**
   - Each cube bound to a data source other than `default` gets its new alias, and its rollups rebuild, at its next publish ([pub] L382, L392-394; [rev] L812).
   - In wechart, a cube is republished only when its YAML changes ([w-cs] L29-32), or when the whole model is sent ([w-sync] L138-143).
7. **No wechart code or test asserts on these aliases or table names.** The e2e table-name checks are for root cubes on the root's `default`, which are unchanged (API surface).
8. **Nothing else is new.** The range has no new route, environment variable, migration or image-check step ([cmp] file list).

### Mapping `dataSource` to wechart's data sources (T459, AC-157)

- **A string `dataSource` is exactly the connection name Cube asks xcube's driver for.**
  - In a model with connections, a connection of that name serves it. Any other name but `default` is refused ([x6] L407-410).
  - wechart names its connections `connectionNameOf(xcubeFolderId, name)`: the bare short name in the root, `<xcubeFolderId>__<name>` elsewhere ([w-conn] L111-113). That is the same rule as xcube's `fullNameOf` ([items] L65-67).
- **So match by exact name** over the data sources whose folder xcube holds (`PublishedFolders.ids`, [w-folders] L95-98):

```ts
// T459 sketch. published: PublishedFolders; sources: DataSource[] (repos/data-sources.ts L28-31)
const byConnection = new Map<string, DataSource>();
for (const source of sources) {
  const xcubeId = published.ids.get(source.folderId);
  if (xcubeId !== undefined) byConnection.set(connectionNameOf(xcubeId, source.name), source);
}
const wechartFolderOf = new Map([...published.ids].map(([id, xcubeId]) => [xcubeId, id])); // 'froot' → 'root'
// For each item with kind 'cube' and typeof item.dataSource === 'string':
//   byConnection.get(item.dataSource)  — 'default' finds the root's `default` row, when wechart has one
```

- **`'default'` with no root `default` row** means Cube's own environment. Only `default` may fall back to it in a model with connections, and compose's `CUBEJS_DB_*` serves it until a root `default` connection exists ([x6] Gotcha 6). No wechart row matches it; how to show it is a T459 UI question.
- **An unbound short name** (a model with no connections) still matches what Cube serves.
  - A folder cube's unbound `warehouse` is served by a root connection named `warehouse` if one exists, and fails otherwise ([x6] L407-410).
  - Matching the bare name therefore agrees with the query path.
- **Folder paths for display.** An item's `folderId` is xcube's (`f` + 32 hex digits, or `froot`). Invert `published.ids` to get wechart's id ([w-folders] L22-25; [w-cat] L68).
- **The client drops both new fields today.**
  - `HeldItem` is `{ folderId, name, fullName, bindings }`, and `items()` copies only those ([w-client] L118-125, L310-337).
  - T459 must parse `kind` and `dataSource` ([w-tasks] L7245).
  - An older image (`ed08180c37`) sends no `dataSource`. Read a cube without the key as "unknown", not as `'default'`.

### Resolving `null` (a cube that `extends` another)

- **Not from `GET …/items` alone, in general.**
  - The child's `bindings` do hold its parent: `bindings[<extends short name>] = <parent full name>` ([rw] L147-153, L160-169, L340-344).
  - But `bindings` holds every name the child uses (joins included), with no mark on which one `extends` names. The resolved YAML, which says `extends: <parent full name>` ([rw] L344), is not in the answer ([rt] L2891-2899).
- **It can be resolved with wechart's own copy of the item**, as follows:
  1. Read `extends:` (a short name) from wechart's YAML for that folder and name.
  2. Take `child.bindings[thatShortName]` as the parent's full name.
  3. Find the parent in the same answer, and use its `dataSource`.
  4. If that is `null` too, repeat, guarding against a loop.
- **Why this is right.** Cube compiles the child with the parent's current definition as its prototype. So the child queries the parent's *current* binding, not the one at the child's publish ([c-sym] L537-541; [u-sym]). wechart's e2e shows it: the child reads `template1` after only its parent was republished ([w-e2e-bind] L256-262).
- **Caveat.** This holds only while wechart's YAML is what xcube published. wechart already compares its items hash with xcube's head `itemsHash` ([w-check] L112; [w-sync] L127).
- **Or ask xcube** to add the parent's full name, or the inherited data source, to `ItemRef` (Open question 1). [req-items] L21 offered `null` as acceptable.

### The SQL alias written at publish

`finish` sets `sql_alias` when the item is in a folder, or when it is a cube with an aliased data source, and no `sql_alias`/`sqlAlias` was authored ([pub] L118-133). The "aliased data source" is `doc.data_source ?? doc.dataSource`, as bound (or written), unless it is the literal `'default'` ([pub] L64-67). The rules:

- **`aliasOf(fullName)`**, with no data source: the full name if it is at most 20 characters, else `x` plus 7 base32 characters of SHA-256(fullName) ([pub] L24, L33-40, L50-52).
- **`aliasOf(fullName, ds)`**: `<fullName>_<4 base32 of SHA-256(ds)>` if that is at most 20 characters, else `x` plus 7 base32 of SHA-256(`<fullName>@<ds>`) ([pub] L53-54).
- **The rollup stem.** If any pre-aggregation's `<alias>_<pa sql_alias or name>` is over 25 characters, the alias becomes the 7-character hash form ([pub] L21, L127-131).

| Cube | `sql_alias` written | Changes with the binding? |
| --- | --- | --- |
| wechart folder cube (full name `f<32 hex>__<short>`, ≥ 36 characters), bound to `default` or naming none with the root's nearest | `x` + hash(fullName), as before | No |
| wechart folder cube bound to a folder's source, a folder's `default` included (`f…__default` is not the literal `default`) | `x` + hash(`fullName@dataSource`) | **Yes** ([t-names] L623-628) |
| Root cube naming none, or bound to the root's `default` | none. Cube uses the cube's name, as before | No ([t-names] L622) |
| Root cube bound to a root source other than `default` | `<name>_<4>` when the name is ≤ 15 characters and no rollup stem is over 25; else `x` + hash(`name@ds`). **New:** root cubes had no alias before | **Yes** ([t-names] L630-631) |
| Any cube with an authored `sql_alias` | The authored one | No ([pub] L125; [t-names] L632) |
| A cube that `extends` another and names no data source | Folder: `aliasOf(fullName)`. Root: none (see Gotcha 3) | No (Gotcha 2) |
| Views | As before (`aliasOf(fullName)` in folders), never by data source | No ([pub] L124) |

- **Uniqueness is still checked across the model.** A clash answers `422 invalid_items` with kind `alias`: `Its SQL alias "<a>" is also <fullName>'s` ([pub] L170-182). The check reads each item's own `sql_alias ?? sqlAlias ?? name` only ([pub] L177).

### What the alias changes for wechart

- **Result cache.**
  - Cube's result key is `[query SQL, values, rollup loadSqls, invalidate]` under `<prefix>#SQL_QUERY_RESULT:`, with no data source ([c-qc] L469-481, L1301-1303; same at the v1.7.45 tag, [u-qc]).
  - The alias appears in the table alias and in every member column (`<alias>__<member>`) ([c-bq] L4229-4246; [pn] "sql_alias, and how Cube builds SQL aliases").
  - So a changed alias means different SQL and a cache miss.
- **Rollup tables.**
  - The logical name is `<schema>.<aliasName("<cube>.<pa alias or name>", true)>`, with the cube part replaced by its `sqlAlias` ([c-scpa] L321, L450-457; [c-bq] L4393-4396; [pn] "Pre-aggregation table names").
  - Cube's docs: `sql_alias` "affects all member names, including pre-aggregation table names" ([d-cube]).
  - So a rebound cube's rollups are new tables, built afresh. Rollups of other cubes that join it change their load SQL, and so their version ([pn] L156-157).
- **Jobs and partitions.**
  - `preAggregationId` is `<cube>.<pa>` by cube name ([c-scpa] L381). Selecting and building by id is unchanged ([w-e2e-switch] L310-317).
  - Only the table text shown changes, for example `job-table` ([w-e2e-jobs] L61-65).
- **The SQL wechart shows** (`/api/sql`, AC-168, [w-server] L713-721) shows the new alias. The acceleration panel reads `preAggregationId` only ([w-server] L685-691).
- **Authored `sql_alias`** (the model form offers it: [w-form] L242, L506, L606) is kept. A rebind of such a cube still answers from the old cache and rollups (Gotcha 4).
- **`extends`:** see Gotchas 2 and 3.

## Gotchas

1. **An alias moves only when its cube is resolved again** ([pub] L382, L392-394).
   - In wechart, that happens when the cube's YAML changes ([w-cs] L29-32), or on a whole-model send, which re-resolves (and rebinds) everything ([pub] L75).
   - Adding a nearer data source rebinds nothing, as before ([x6] Gotcha 5).
2. **A folder cube that `extends` a rebound parent keeps its alias, and republishing it doesn't help.**
   - **Its binding follows the parent.** The child names no data source, so `bindDataSource` writes none ([pub] L266). The child compiles against its parent's current binding through Cube's prototype ([c-sym] L537-541; [w-e2e-bind] L261-262).
   - **Its alias doesn't.** `aliasedDataSource` reads only the child's own `data_source` ([pub] L64-67, L124). The child's alias stays `aliasOf(fullName)` whenever it is published.
   - **Its SQL doesn't either.** The inherited `sql` has the same text, so the child's result-cache key and rollup table names don't change when the parent is rebound. The child can answer from the old source's cache (under the default `stale-if-slow`, while the refresh key is unchanged) and from its inherited rollups ([c-qc] L469-481; [c-sym] L407-412; [rjc] L298, L304).
   - **xcube's advice doesn't hold.** "When only its parent is rebound, publish the child again too" ([ans] L26; [readme] L493-495) is contradicted by reading: the republished child gets the same alias. No xcube test covers aliases under `extends`.
3. **A root cube that `extends` a root parent on a non-`default` source takes its parent's alias.** By reading; untested; the Cube lines are the checkout's, with `setPrototypeOf` confirmed at the v1.7.45 tag ([u-sym]).
   - **Why.** The root child gets no `sql_alias` (not prefixed, no data source: [pub] L119, L124-125). Cube looks `sqlAlias` up through the prototype, which is the parent's built cube ([c-sym] L343-350, L537-541; [c-ev] L250-266; [c-bq] L4234-4238). The parent now has an alias ([pub] L125). The docs don't say how `sql_alias` behaves under `extends` ([d-cube]).
   - **Consequences.** The child shares the parent's member aliases. Inherited pre-aggregations ([c-sym] L407-412) get the parent's logical table names. xcube's uniqueness check reads own aliases only ([pub] L177), so it doesn't catch this.
   - **Before this commit,** this happened only with an authored alias on a root parent.
4. **Authored `sql_alias` opts out.** Rebinding such a cube still serves the old cache and rollup tables ([pub] L125; [readme] L491-492).
5. **A connection changed in place keeps its cubes' aliases.** Cached answers and rollups built from the old target renew on refresh keys only ([readme] L496-498).
   - Cube's defaults are `every: '10 second'`, or `'2 minute'` for BigQuery, Snowflake and others ([rjc] L299).
   - Rollups follow their own refresh keys.
6. **The rollup half of the fix is untested.** The new test's cube has no pre-aggregation ([t-conn] L541-546). The rollup claim rests on reading [c-bq] L4393-4396.
7. **xcube's test asks in the default cache mode, not the one it names.**
   - `cacheMode` inside the query JSON ([t-conn] L548-550) is overwritten: `normalizeQueryCacheMode(query, cacheMode)` sets `'stale-if-slow'` when neither the request's `cache` nor `query.cache` is set ([u-q]; [c-q] L413-424). `GET /v1/load` passes only `req.query.cache` ([u-gw]; [c-gw] L380-388).
   - The test still shows the fix for Cube's default mode, which is what wechart's queries use unless they pass `cache` ([rjc] L301-304).
8. **Old rollup tables stay behind** after an alias moves. Whether Cube drops logical tables no pre-aggregation uses any more is UNVERIFIED ([x6] Gotcha 12).
9. **A short root name gets only 20 bits of data-source hash.**
   - `<name>_<4>` uses 4 characters of 5 bits each ([pub] L33-40, L53). A rebind between two data sources whose 4-character hashes collide (1 in 2^20 per pair) keeps the alias, and so the old cache.
   - Hashed aliases use 35 bits over `fullName@dataSource` ([pub] L54). A clash with another cube's alias is refused (`422`, [pub] L178-182), never silent. By reading.
10. **Rolling upgrades.** While old and new images serve publishes side by side (Helm runs `cube.replicas` 2, [w-deploy] L12), the same cube can be given the old or the new alias depending on which process publishes it. Each change is another rebuild. By reading.
11. **Overlays follow the same rule.** Previews publish through the same `publish` → `finish` ([rt] L1447-1470). An overlay's copy under a published full name gets the same alias as the published cube. Such previews compile apart, on their own orchestrator and cache ([rt] L1425-1438; [xov] L438-439).
12. **`/items` lists the head only.** It holds no workspace overlays or drafts, and no folder filtering ([rt] L3215-3226; [routes] L529-536).
