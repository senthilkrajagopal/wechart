## Summary

**What slice 5 builds** ([p5] message; [readme@c] "Overlays"):
1. **Stored overlays.** A workspace's or a proposal's unpublished items are stored per model as an overlay. The routes are `PUT`, `GET` and `DELETE …/overlays/{id}` ([routes@c]), over the table `overlays` of migration 5 ([mig] L163-192).
2. **A signed claim names the overlay.**
   - The claim is named by `config()`'s new `overlayClaim` option, whose default is `xcubeOverlay`, **not** `wechartOverlay` ([cfg@c] `serving`).
   - The RS256 verifier copies that claim into the security context ([ver] L169, L177-178).
   - `pinFor` then serves the request from the overlay in place of the published revision, and sets `x-xcube-overlay` ([rt@c] `pinFor`).
3. **Live.** An overlay is applied, at query time, to the revision the answering instance serves ([rt@c] `overlayRevision`, `buildOverlay`). It is compiled under a key naming that base revision, the overlay's version and the model's permissions version ([rt@c] `overlayKey`).
4. **Only changed modules compile.** Unchanged modules are the published ones ([rt@c] `applyOverlay` → `moduleGroups`; [t-ov] L243-258).
5. **Rollups are stripped** from every item the overlay's changes reach, from those items' `extends` ancestors, and from what those ancestors reach ([rollups] L42-63).
6. **A push is taken only if it applies and compiles.** Otherwise it answers `422 invalid_items`, and the stored overlay is untouched ([rt@c] `putOverlay`).
   - `baseVersion` orders racing pushes.
   - Versions come from one sequence, so they only go up, across drops too ([mig] L173-179).
7. **Drops and expiry.** A push or a drop notifies every instance ([rev@c] `putOverlay`, `deleteOverlay`; [lst@c]). A dropped or expired overlay answers `410`, and one that no longer applies answers `409` ([rt@c] `gone`, `brokenOverlay`).
8. **`POST …/resolve` takes `overlay`** ([routes@c] `resolveSchema`; [rt@c] `resolveNames`).
9. **Memory is bounded.** Compiled overlays retire after `XCUBE_OVERLAY_IDLE_MS` (10 min). At most `XCUBE_MAX_ACTIVE_OVERLAYS` (50) stay compiled per instance, least recently used first ([set@c]; [rt@c] `makeRoomForOverlay`, `retireDue` hunk).
10. **Two other changes:**
    - `unverified` now strips `xcubeModule` ([rt@c] `unverified`);
    - the permissions hash now covers each folder's parent ([rev@c] `touchPermissions`).

## Init / auth pattern

### `cube.js`

- **Name the claim.** The committed `config()` is `overlayClaim: options.overlayClaim ?? 'xcubeOverlay'` ([cfg@c] `serving`). The verifier uses the same default ([rt@c] `new TokenVerifier(…, { overlayClaim: () => this.options?.overlayClaim ?? 'xcubeOverlay' })`).
- **wechart's `cube.js` passes only `modelClaim` and `revisionClaim`** ([w-cube] L17-18). It must become:
  ```js
  module.exports = require('xcube').config(
    { modelClaim: 'wechartModel', revisionClaim: 'wechartRevision', overlayClaim: 'wechartOverlay' }, { … });
  ```
  This is exactly what xcube's image check writes ([sh@c]). Gotcha 1 gives the reasons.

### Admin calls

- **The overlay routes and `POST …/resolve` use the admin `auth` middleware** ([routes@c]). As in slice 4, that is the service token, or an `XCUBE_ADMIN_TOKENS` entry while one is set ([x4] "Admin authentication").
- **A model-named service token** is confined to its model ([x4]).
- **Tested with each credential:** the integration suite uses a static admin token ([t-ov] L27, L180), and the image check uses the service token ([sh@c]).

### Query tokens

A preview's user token is the slice-4 token plus one claim (load-bearing):
```jsonc
header:  { "alg": "RS256", "kid": "<kid of a key pushed for this model>" }
payload: { "aud": "xcube", "role": "user", "iat": …, "exp": …,
           "groups": ["g-sales"], "iss": "<the key set's issuer, when it names one>",
           "wechartModel": "<model>", "wechartRevision": 12,
           "wechartOverlay": "<workspace or proposal id>" }
```
- **The verifier builds the context** `{ wechartModel, groups, wechartRevision?, wechartOverlay?, xcubeRole: "user" }`. It copies the overlay claim whenever the token carries it ([ver] L168-181).
  - Tested: unit test "a user's token: its model, groups and revision, and nothing else of it", which asserts `wechartOverlay: 'ws-1'` ([t-usec]).
- **`overlayOf` checks the claim** ([rt@c] `overlayOf`):
  - `undefined` or `null` means no overlay;
  - anything that isn't a string matching `^[A-Za-z0-9_-]{1,64}$` answers `403 "Invalid overlay id in the security context"` ([t-ov] L389).
- **HS256 tokens carry the claim too** until the model has keys:
  - `unverified` strips only `xcubeRole` and `xcubeModule` ([rt@c] `unverified`);
  - the integration suite signs every preview HS256 ([t-ov] L183).
- **Service tokens can't name an overlay.** Their context is `{ wechartModel?, xcubeRole }` ([ver] L194-210).

### `PUT …/overlays/{id}`

- **Request** ([routes@c] `overlaySchema`, `itemSchema`, `itemRefSchema`):
  ```ts
  {
    upserts?: { folderId: string /* ≤64 */; name: string /* ≤64 */; kind: 'cube' | 'view'; yaml: string }[]; // ≤ 2000, default []
    deletes?: { folderId: string; name: string }[];                                                     // ≤ 2000, default []
    ttlSeconds?: number;          // integer ≥ 1; clamped to XCUBE_OVERLAY_MAX_TTL_S
    baseVersion?: number | null;  // integer ≥ 1, or null
  }
  ```
- **What it does, in order** ([rt@c] `putOverlay`):
  1. **No head** → `unknown_model`. A files-mode head → `mode`.
  2. **`baseVersion`.** When given, it must equal the live overlay's version, with `null` meaning none. Otherwise → `conflict` with `currentVersion`. This runs before any compile.
  3. **The limit.** A new id when the model already has `max` live overlays → `too_many_overlays`.
  4. **`expiresAt`** = now + `min(ttlSeconds ?? ttlS, maxTtlS)`.
  5. **`contentHash`** = SHA-256 of `[itemsHash(upserts), sorted "folderId/name" of the deletes]`.
  6. **`applyOverlay`** over the current head's items and folder tree. Name errors return `invalid` with no compile.
  7. **The compile.** It is skipped only when the stored overlay has the same `contentHash`, `validatedRevision === head.revision` and the same folder-tree hash. Otherwise `validateModules(…, Priority.DryRun, {}, [])` compiles the changed modules: no probes, an empty security context.
  8. **The store write** ([rev@c] `putOverlay`), in one transaction under the model's row lock:
     - it deletes that model's expired rows;
     - it re-checks `baseVersion` and the limit;
     - it upserts with `version = nextval(overlay_versions)`, but keeps the old version when `content_hash` is unchanged;
     - it sends `pg_notify(…, {model, overlay: id, version})`.
  9. **The answering instance** applies it at once (`overlayChanged`).
- **What `applyOverlay` checks** ([rt@c] `applyOverlay` → `publish({ …, lenientDeletes: true, overlay: true })`; [pub@c]):
  - **Folders.** Each upsert's and delete's folder must be in the tree: an error of kind `folder`.
  - **Replacement.** An upsert replaces the published item with the same `folderId/name`.
  - **No two upserts share a short name** across folders: kind `item`, message `The overlay holds two items named "<n>" (in <a> and <b>); names in it resolve to its own items first, so they must differ` ([pub@c]; [t-names] "an overlay may not hold two items of one name").
  - **Deletes.** Deleting an absent item is no error (`lenientDeletes`). Deleting an item that a kept item binds to is `422` (kind `reference`), as in 3a ([x3a] "Removal and renames").
  - **Every other 3a item rule applies** ([x3a] "Item content", "Names"; [x4] the reserved-group refusal).
- **Answers** ([routes@c] PUT):
  - `201` for a new id, `200` otherwise: `{ model, id, version, created, revision, expiresAt, items }`;
  - `revision` is the head it was checked against;
  - `items` is `[{ folderId, name, fullName }]` for the **upserted** items only ([rt@c] `refs(applied.items, changed)`; [t-ov] L224-225).
- **Tested** ([t-ov]):
  - created, then `GET` shows `validatedRevision` and `idle` (L222-228);
  - the same content again → `200`, `version` unchanged, `created: false`, `expiresAt` later (L279-283);
  - a push that doesn't compile → `422 invalid_items`, errors placed on `fb/gadgets`, and the previous version still answers (L285-291);
  - `baseVersion: null` twice → `201` then `409`; a stale one → `409 conflict` with `currentVersion`; the current one → `200` (L339-347);
  - the limit (L348-358);
  - a dropped id pushed again gets a higher version and new content (L362-374; [t-perm] L199-201 at the commit).

### `GET …/overlays/{id}`

- **Answer** ([rt@c] `overlayStatus`):
  ```ts
  { model, id, version, expiresAt /* ISO */, validatedRevision: number | null,
    upserts: { folderId, name, kind }[],   // no yaml
    deletes: { folderId, name }[],
    instance: { revision: number | null /* this instance's active revision */,
                state: 'serving' | 'idle' } |
              { revision, state: 'broken', errors: ItemError[], cubeMessage: string | null } }
  ```
- **`instance` is this instance's view** (Gotcha 7):
  - `broken`: this instance tried the overlay over its active revision and failed, within `XCUBE_OVERLAY_IDLE_MS`;
  - `serving`: it holds it compiled and active;
  - `idle`: anything else.
- **`404 unknown_overlay`** when no live row exists: expired, dropped or never pushed ([rev@c] `overlay` filters `expires_at > now()`).
- **Tested:** `idle` after a push (L227); `broken` with `errors[0]` on `fb/report` after a breaking publish (L311-313); `404` after a drop (L380). A `404` after expiry is by reading.

### `DELETE …/overlays/{id}`

- **`204` whether or not the overlay existed** ([routes@c] DELETE; [t-ov] L377-378). An invalid id is `400`, and the credential rules apply.
- **What it does.** It deletes the row and sends `pg_notify(…, {model, overlay: id})` ([rev@c] `deleteOverlay`). The answering instance then runs `overlayChanged`: it bumps a generation, drops its cached record and marks compiled versions as retiring ([rt@c] `deleteOverlay`, `overlayChanged`).
- **Previews answer `410` from then on** ([t-ov] L379, L381):
  - on another instance, on its notice. Tested within 2 s, not after the 30 s cache ([t-perm] L183-203 at the commit);
  - with notifications down, another instance's cached record lasts up to 30 s ([rt@c] `overlayRecord`).

### `POST …/resolve` with `overlay`

- **Request:** `{ folderId, names: string[] /* ≤1000, each ≤64 */, overlay?: string /* OVERLAY_ID */ }` ([routes@c] `resolveSchema`).
- **What it does** ([rt@c] `resolveNames`, from [d5]'s hunk, matching the tree):
  1. It reads the live overlay, or throws `410`.
  2. It removes the overlay's deletes from the published items and adds its upserts.
  3. For each name, **an overlay upsert of that short name wins, whatever its folder**. Otherwise the nearest folder on `folderId`'s path wins. Otherwise `null`.
- **Answer:** `{ model, revision, folderId, overlay, names: { [name]: fullName | null } }`.
- **Tested** ([t-ov] L260-266). From `fb`, with `overlay: ws1`:
  - `widgets` → `fc__widgets`, the overlay's copy from `fc`, a folder off `fb`'s path;
  - `orders` → `fa__orders`;
  - `customers` → `customers`;
  - `nothing` → `null`.
  - Without `overlay`: `widgets` → `null`.
- **It applies to the current head** and doesn't check that the overlay compiles.

### How an overlay is compiled and served

- **Composition with later publishes** ([rt@c] `overlayRevision`, `buildOverlay`, `overlayKey`):
  - the key is `xcube:<model>:o:<id>:<version>:t<permissionsVersion>@<base revision key>`;
  - so a new published revision, a new overlay version, or any folder, group or security change makes a new key, and the first query then builds it;
  - the build applies the stored changeset to the base's items with `publish(…, overlay: true)`.
  - Tested: after an unrelated publish the preview still answers, and sees the new cube `extra` (L294-303); after a publish that deletes `customers`, which the overlay's `report` joins, it answers `409` (L305-310).
- **What a later publish does to the overlay's items:**
  - an upsert keeps replacing the published item of its `folderId/name`, even if a later publish changed that item (Gotcha 6);
  - published items keep their stored bindings ([t-names] "an overlay item's names resolve in the overlay first…", which asserts `fsales__orders` keeps `customers`);
  - an overlay item's names resolve in the overlay first, then along its folder's path ([rw] L27-31, L39-48, L80; [t-names]).
- **Only changed modules compile** ([rt@c] `applyOverlay` → `moduleGroups(previous, …)`).
  - Tested with `packMin: 1` (L137): one new module, the one holding `fa__orders` and `fa__v_orders`, was compiled; the rest were the published ones (L243-258).
  - With default packing a small model is one module ([x3b] L124). Then every overlay compiles the whole model (Gotcha 8).
  - `validateModules` compiles the whole file set when there is at most one module (working `runtime.ts` `validateModules`, the method [x3b] L188 describes).
- **Concurrent first queries share one build** (`overlayBuilds`; [t-ov] L330-337: 6 queries, all `200`).
- **Breaks are remembered.** A build that fails with errors placed on items is remembered by key as broken. Later queries answer `409` at once, until the entry ages out after `idleMs` or any notice for that id clears it ([rt@c] `buildOverlay`, `overlayChanged`, `retireDue` hunk).
- **Rollups** ([rollups] L12-31, L48-63, L70-84):
  - **What is stripped.** `rollupsToStrip` takes every item bound to a changed item, however indirectly (joins, `extends`, member SQL, views). It adds their `extends` ancestors, however far up, and then everything bound to those ancestors. It repeats until nothing is added.
  - **How.** `withoutRollups` deletes `pre_aggregations` and `preAggregations` from those files.
  - **Tested:**
    - `/v1/sql` on a changed cube lists 1 rollup published and 0 in the preview; the view over it reads the source too (L268-277);
    - an override (`orders_x extends base_orders`) loses the inherited rollup, and an unreached cube keeps its own (L316-328);
    - unit tests "what an overlay's changes reach…" and "an item without its pre-aggregations…" ([t-uov]).
  - **`parentOf` reads `extends` with a regex over xcube's own YAML dump** ([rollups] L33-40). By reading.
- **Caching and memory:**
  - an overlay record is cached 30 s, or 2 s when absent, at most 10,000 entries per instance, and re-read at once on a notice ([rt@c] `overlayRecord`);
  - compiled overlays: at most `maxActive` active per instance, least recently used retired first ([rt@c] `makeRoomForOverlay`);
  - one unused for `idleMs` is marked retiring on the periodic check, and compiled again on next use ([rt@c] `retireDue` hunk; [x3b] L288, L161). Idle retirement is untested.
  - Cube's result cache is keyed by SQL with no data source ([w-rt] L395). At `d26ff4238e` overlays bring no data sources, so a preview query with the same SQL as a published one shares its cached result.

### Lifetime and cleanup

- **Expiry counts from each push**, including a same-content push. It is never extended by queries ([rt@c] `putOverlay`; [rev@c] `putOverlay`).
- **Expired rows are invisible at once** (`expires_at > now()` in `overlay` and `overlayCount`). They are deleted only by the next `PUT` for the same model ([rev@c] `putOverlay`). No other code at the commit deletes them (fetch of [rev@c], asked for every `DELETE FROM … overlays`).
- **Rows cascade** when the model row is deleted ([mig] L177).

### Migration and rollback

- **Rolling forward.** Migration 5 is additive with `minReader: 2` ([mig] L163-167).
  - A slice-2 to slice-4 image on a v5 schema logs "the schema has migrations newer than this xcube; running on" and serves ([migrate] L101-107).
  - Migration 4's `min_reader` still decides whether 3a or 3b images may start ([migrate] L95-100; [x4] Gotcha 13).
- **Rolling back to slice 4** leaves the `overlays` table unread. Previews are then answered from the published model with `200`, because slice 4 ignores the claim (Gotcha 2).
- **No overlay push checks for older instances at the commit.** `olderInstances(client)` has no version argument and is called only from `putFolders` ([rev@c]).
- **The permissions-hash formula changed**: it is now over `[security, [[id, parentId, groups]…]]` ([rev@c] `touchPermissions`).
  - So the first folder write after the upgrade bumps `permissions_version` once even if nothing changed. By reading.
  - While slice-4 and slice-5 instances both write folders, their writes can bump it alternately.

### T347 (AC-281, AC-283, AC-323, AC-329)

- **Files.** The routes are `{CUBE_API_URL}/v1/semantic/models/{model}/overlays/{id}` ([routes@c]), not `/v1/semantic/overlays/{id}` ([w-tasks] L5547).
- **Id.** 1-64 of `[A-Za-z0-9_-]` ([rt@c] `OVERLAY_ID`). A UUID fits.
- **Push on every save** with `baseVersion`: `null` for the first push, then the last `version` returned. A `409 conflict` carries `currentVersion` ([routes@c]).
  - A same-content push is cheap: no compile unless the head or the tree moved. It is also how to extend the life.
- **Place each item** in its origin folder (a copy) or its target folder (a new item). No two may share a short name ([pub@c]).
- **Expiry.** 24 h after the last push by default, and at most 7 days. Previews of an expired overlay answer `410`, so re-push from wechart's stored workspace before previewing, or on `410`.
- **Drop** on publish or discard (AC-323).
- **Failing-test bullets against xcube:**
  - "Uses the workspace's `sales` over its origin's" and "a copied item resolves along its origin's path, a new one along its target's": xcube's behaviour ([t-ov] L260-266; [t-names]).
  - "Every model … the user may see can be used there" (AC-283): xcube resolves only overlay-first, then along the item's path. A cube in a folder off that path is reachable only by copying it into the overlay ([t-ov] L196-197, L263). Data sources: at `d26ff4238e` an overlay brings none. Workspace data sources (AC-280) are the uncommitted overlay-connection work, not this commit (Provenance).
  - "Answers only its owner" (AC-323): enforced only by which tokens wechart signs (Gotcha 3).
- **Pickers (AC-329).** Resolve with `overlay`, for workspace items only. It resolves overlay-first for any `folderId`.

### T350 (AC-285)

- **One overlay per proposal** (`<proposal id>`) can hold the dashboard's workspace-only models with the dashboard's own model items. The push's `422` is the propose-time compile check ([in] L40). It runs no probes ([rt@c] `putOverlay`).

### T440 (AC-323)

## Gotchas

1. **The default claim name is `xcubeOverlay`.** wechart's `cube.js` doesn't set `overlayClaim` ([w-cube] L17-18; [cfg@c]). Until it does:
   - an RS256 `wechartOverlay` is dropped by the verifier ([ver] L169, L178);
   - an HS256 one reaches the context, but `overlayOf` reads `xcubeOverlay`;
   - either way the query is answered from the **published** model with `200`.
   - With the default, an HS256 preview context holding `xcubeOverlay` is not stripped by wechart's `previewClaimsOf`, which strips `wechart*` only ([w-client] L401-414). Set `overlayClaim: 'wechartOverlay'`.
2. **Mixed versions answer silently from the published model.**
   - A pre-slice-5 instance ignores the claim.
   - No overlay push checks for older instances at the commit ([rev@c] `putOverlay`).
   - During a rolling upgrade or rollback, a preview can get `200` from the published model. Check `x-xcube-overlay` on each answer.
3. **The overlay id is a bearer capability.** The claim names the id, not a version or a user:
   - any token for the model naming it previews it;
   - a token still within its `exp` (wechart's are 300 s, [w-client] L80) outlives a membership change;
   - a token also outlives a drop and re-push of the same id, and then reads the **new** content.
   - AC-323 therefore rests on wechart's signing, and on keys being pushed so that HS256 is refused ([x4]).
4. **HS256 names any overlay** until the model has keys ([rt@c] `unverified` strips only `xcubeRole` and `xcubeModule`; [t-ov] L183). Anyone holding `CUBEJS_API_SECRET` can preview any overlay then.
5. **An overlay's resolution isn't a changeset's.**
   - In an overlay, an item's names resolve among the overlay's items first, by short name, whatever their folder ([rw] L39-48, L80; [pub@c]).
   - Published or landed, they resolve nearest-first along the item's path ([t-names] "without the overlay, the same items resolve nearest-first as ever").
   - So a proposal whose overlay compiles can bind differently, or fail, when its items land by changeset. The copy of `widgets` from off-path `fc` in [t-ov] L196-197 is such a case.
6. **No per-item base check.** An overlay upsert replaces the published item of that `folderId/name` whatever was published since ([pub@c]: upserted keys replace kept ones). A change published to that item after the workspace copied it is hidden in the preview, and nothing reports it. By reading.
7. **`GET`'s `instance` is one instance's view.**
   - `broken` appears only after that instance tried the overlay over its current revision, and only for `idleMs`, or until any push or drop of the id clears it ([rt@c] `overlayStatus`, `overlayChanged`).
   - With 2+ Cube instances ([w-spec] AC-319), `GET` may answer `idle` for an overlay whose previews answer `409` elsewhere.
   - Two dependable sources of the errors:
     - the `409`'s own message, which names up to 3 items;
     - a re-push of the same content, which re-validates against the current head, answers `422` with every error, and leaves the stored overlay as it was ([rt@c] `putOverlay`).
8. **With default packing, today's model is one module** ([x3b] L124). Every overlay then compiles the whole model, on push and on the first preview per instance, and holds a whole compiled copy per instance.
   - [w-wmp] L527 measured 87-182 MiB per resident full-model overlay at 3k-6k cubes.
   - [in] L76's "small, usually under a second" holds for a multi-module model's changed modules. UNVERIFIED for either.
9. **The first preview can wait for the compile lane.** It answers `503` "Cube is busy compiling; try again" with `Retry-After` ([rt@c] `pinFor`), which [x3b] L502 puts at `compileWaitMs/1000` (120). wechart's catch-up retry doesn't cover it ([w-client] L41-42).
10. **A same-content push is re-validated when the head or the folder tree moved.** It can be refused `422` though nothing in the workspace changed, and the stored overlay then keeps its old `validatedRevision` ([rt@c] `putOverlay`).
11. **`ttlSeconds` sets the expiry, it doesn't only extend it.** Each push sets now + `ttlSeconds`, so a smaller value shortens the life. Above 7 days it is clamped silently ([rt@c] `putOverlay`).
12. **Deletes are narrow.** They are lenient about absent items. A delete of an item any kept item binds to is `422` ([x3a] "Removal and renames").
13. **The applied model must fit the snapshot limits.** An overlay push can answer `413 too_large` for the model's size, not the overlay's ([rt@c] `putOverlay` → `checkedSnapshot`; [snap] L71-74). By reading.
14. **`GET` doesn't return YAML.** `upserts` are `{ folderId, name, kind }` only ([rt@c] `overlayStatus`). wechart must keep the workspace's content itself.
15. **Rollups are stripped more widely than the input says.** Stripping also covers everything bound to an extended ancestor ([rollups] L61). A cube joined to `base_orders` loses its rollup in a preview whose overlay changes `orders_x extends base_orders`. The acceleration panel on a workspace item will show no rollups for reached items.
16. **The permissions version now moves on folder moves** ([rev@c] `touchPermissions`). Every overlay's key includes it ([rt@c] `overlayKey`), so any folder move, group change or security toggle recompiles each overlay on its next query.
17. **With notifications down,** a push or drop reaches other instances only when their cached record expires: up to 30 s ([rt@c] `overlayRecord`).
18. **`/v1/meta` differs per overlay.** A meta cache keyed by groups alone serves the wrong field list to a workspace ([w-server] L326-329).
