# Supporting utilities

## Summary

Small libraries shared between wechart's API (Node 26) and web app (Vite/React), used for: runtime validation of Cube query/response shapes (`zod`), structured API logging (`pino`, AC-016), CSV export (AC-171/172/173), and date/time-range display for time dimensions (AC-083). Number/currency formatting for AC-046 is evaluated against `Intl.NumberFormat` plus Cube's own format vocabulary.

## 1. zod

- **Version**: `zod@4.6.5`, MIT license, zero runtime dependencies, works in Node and all modern browsers — [homepage](https://zod.dev/), [registry](https://registry.npmjs.org/zod/latest).
- **Type inference**: `z.infer<typeof schema>` derives a TypeScript type from a schema; this is the mechanism for sharing one schema between API and browser without duplicating types — [zod.dev](https://zod.dev/).
- **v3→v4**: v4 is ~2.3x smaller (core bundle 12.47kb→5.36kb) and up to ~14x faster for string parsing per Zod's own Moltar benchmark; error customization is unified under a single `error` param replacing `message`/`invalid_type_error`/`required_error`/`errorMap`; refinements now live inside the schema chain (`.refine().min()` now works) instead of wrapping in `ZodEffects`; string-format validators (`.email()`, `.url()`) moved to top-level functions, old methods deprecated but present — [zod.dev/v4](https://zod.dev/v4).
- **Bundle size nuance**: Zod's own bundle-size page reports 5.36kb–5.91kb gzip for a tree-shaken minimal import of regular `zod`, and a separate functional `zod/mini` entry point (2–4kb gzip) for bundle-constrained front ends. Bundlephobia reports the _whole package_ (all exports, unshaken) at ~88.6kb gzip — that number is not representative of what ships to the browser after tree-shaking; cite zod's own page, not bundlephobia, for browser-bundle decisions — [zod.dev/packages/mini](https://zod.dev/packages/mini), [bundlephobia](https://bundlephobia.com/api/size?package=zod@4.6.5).
- **Recommendation**: use regular `zod` (not `zod/mini`) in both API and web app — Zod's own docs say bundle size at this scale only matters for bundle-constrained mobile front ends, and the chained API is what the rest of the ecosystem (react-hook-form resolvers, etc.) expects — [zod.dev/packages/mini](https://zod.dev/packages/mini).
- **Needed at all?** Yes. Node 26 and browsers have no built-in runtime schema validator; TypeScript types alone don't validate data crossing the Cube REST/SQL API boundary.

## 2. pino

- **Version**: `pino@10.3.1`, MIT license, deps are pino's own micro-packages (`sonic-boom`, `thread-stream`, `@pinojs/redact`, etc.) — [registry](https://registry.npmjs.org/pino/latest).
- **Structured logging**: pino emits newline-delimited JSON (NDJSON); NDJSON is described as "perfect for production usage and long-term storage" — [pino pretty docs](https://raw.githubusercontent.com/pinojs/pino/main/docs/pretty.md).
- **Redaction**: pino does **not** redact anything by default — you must set the `redact` option (array of paths, or object with `paths`/`censor`/`remove`). Paths use ECMAScript-like lookup (`a.b.c`, `a["b-c"].d`, wildcards `a.b.*`/`a[*].b`), default censor value is `"[Redacted]"`, and `remove: true` drops the key entirely. Non-wildcard redaction costs ~2% serialization overhead; wildcard redaction can cost ~50% — [redaction.md](https://raw.githubusercontent.com/pinojs/pino/main/docs/redaction.md).
- **Child loggers**: `logger.child({...bindings})` attaches fields to every subsequent log line; creation and per-log overhead are both negligible per pino's own benchmarks. Docs explicitly warn not to pass user-controlled data as binding _keys_ — nest untrusted values under a fixed key instead — [child-loggers.md](https://raw.githubusercontent.com/pinojs/pino/main/docs/child-loggers.md). This is the mechanism for a per-request logger carrying a request id, useful for AC-016's per-query record.
- **Pretty-printing**: use the separate `pino-pretty` transport in development only; docs explicitly say it is not for production, and note `logger.flush()` does not work when `pino-pretty` is the transport — [pretty.md](https://raw.githubusercontent.com/pinojs/pino/main/docs/pretty.md).
- **How ours should behave relative to Cube**: Cube's own `CUBEJS_LOG_REDACTION` env var (backing `logRedaction`) defaults to `'false'` in dev mode and `'true'` whenever `NODE_ENV === 'production'` (or dev mode is off), and when on, Cube redacts SQL literal values out of its own logs via `redactSqlLiterals` before logging a query — [cubejs-backend-shared/env.ts](https://raw.githubusercontent.com/cube-js/cube/master/packages/cubejs-backend-shared/src/env.ts), [cubejs-api-gateway/gateway.ts](https://raw.githubusercontent.com/cube-js/cube/master/packages/cubejs-api-gateway/src/gateway.ts). Cube's own gateway also strips stack traces and request ids from responses outside dev mode. Since AC-016 requires wechart to log "the Cube request" for every query, our pino logger must apply the same production-only posture: configure `redact` for filter _values_, security-context/JWT fields, and connection strings, gated the same way (default off in dev so engineers can see raw SQL/filters, default on whenever `NODE_ENV=production`), rather than leaving pino's no-redaction default in place.

## 3. CSV export (AC-171/172/173)

Compared `papaparse@5.7.0` (MIT, zero deps) vs `csv-stringify@6.8.3` (MIT, zero deps) vs hand-rolled — [papaparse registry](https://registry.npmjs.org/papaparse/latest), [csv-stringify registry](https://registry.npmjs.org/csv-stringify/latest).

|                         | papaparse `Papa.unparse`                                                                                                                                                                                                                                                                                                                           | csv-stringify                                                                                                                                                                               |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Environment fit         | Built for the browser (also runs in Node); natural fit if export is generated client-side from data already in the tile                                                                                                                                                                                                                            | Built as a Node.js `stream.Transform`; also ships Node ESM/CJS **and** browser ESM/IIFE builds — [csv.js.org/stringify](https://csv.js.org/stringify/)                                      |
| Quoting                 | `quotes` option: `true` forces quoting on all fields, or an array/function to quote per-column/cell; ignored for `undefined`/`null`/date objects — [papaparse docs](https://www.papaparse.com/docs)                                                                                                                                                | Separate `quoted`, `quoted_string`, `quoted_empty`, `quoted_match` options plus raw `quote`/`escape` chars for fine-grained control — [csv.js.org/stringify](https://csv.js.org/stringify/) |
| Formula-injection guard | `escapeFormulae` option prepends `'` to cells starting with `=`,`+`,`-`,`@`,tab,CR — directly relevant since exported measure/dimension values could start with those characters — [papaparse docs](https://www.papaparse.com/docs)                                                                                                                | Not called out in the docs fetched; would need a manual `cast` function                                                                                                                     |
| BOM for Excel           | No dedicated "auto-prepend BOM" flag was found in the unparse config surfaced by the docs fetched — `Papa.BYTE_ORDER_MARK` is documented as a parse-time recognized delimiter constant, not confirmed as an unparse output option — **UNVERIFIED**: whether `Papa.unparse` can auto-emit a BOM, vs. requiring the caller to prepend `'﻿'` manually | Has a first-class `bom` option "which supports Excel compatibility by adding appropriate encoding markers to output files" — [csv.js.org/stringify](https://csv.js.org/stringify/)          |
| Streaming large exports | `step`/`chunk` callbacks exist but are documented for **parsing**, not for `unparse`; no streaming write API was found in what was fetched                                                                                                                                                                                                         | Native fit: "Extends the native Node.js streaming API," implements `stream.Transform`, explicitly designed for big datasets — [csv.js.org/stringify](https://csv.js.org/stringify/)         |
| License                 | MIT                                                                                                                                                                                                                                                                                                                                                | MIT                                                                                                                                                                                         |

- **Recommendation**: if export generation happens in the browser from an already-fetched result set (consistent with AC-171's "matches what the tile shows"), use `papaparse@5.7.0`'s `unparse`, and manually prepend `'﻿'` to the output `Blob`/string for Excel BOM compatibility (confirm the exact API before relying on any built-in BOM flag — flagged as unverified above). If export ever needs to stream very large result sets from the API/Node side, `csv-stringify@6.8.3`'s stream interface is the better fit; it can be added later without conflicting with papaparse in the browser.
- **papaparse 5.7.0 `unparse`, read from its source (`papaparse.js` in the 5.7.0 tarball, `npm pack papaparse@5.7.0`), 2026-09-22, for T177:**
  - `escapeFormulae` takes a boolean or a **RegExp** (line 294). `true` means `/^[=+\-@\t\r].*$/` (line 297). It is tested only against **string** values (line 380), and an escaped field is also quoted.
  - The default newline is `'\r\n'` (line 193).
  - A field is quoted when it holds the delimiter, a quote, `\r`, `\n` or the BOM, or starts or ends with a space (lines 385-395).
  - There is **no BOM option** for `unparse`. `Papa.BYTE_ORDER_MARK` is the constant `'﻿'` (line 67), which the caller prepends. This resolves the UNVERIFIED item below.
  - Cube sends numbers as JSON strings (research/cube/data-apis.md, "Values are JSON strings"), so the default `true` would turn `-5` into `'-5`. A RegExp that leaves plain numbers alone keeps raw numeric values intact (AC-173).
- **Hand-rolled CSV**: rejected — correct CSV quoting/escaping (embedded commas, quotes, newlines, leading `=`/`+` formula-injection characters) is exactly the kind of edge-case-heavy logic both libraries already solve and test; writing it by hand risks violating AC-171's "match what the tile shows" on edge-case values.
- **AC-172 (truncation)**: neither CSV library reports "how many rows Cube returned before a limit" — that count must come from the Cube query response/metadata itself (row count vs. requested limit) and be surfaced by wechart's own export code, independent of which CSV writer is used.
- **AC-173 (formats vs. raw numbers)**: neither library formats values — formatting must happen in wechart before handing rows to the writer: pass the Cube-formatted _display_ string for dimensions but the **raw numeric** value for measures, per AC-173, using the format layer described in section 5 below.

## 4. Dates (AC-083)

- **date-fns**: `date-fns@4.4.0` — [registry](https://registry.npmjs.org/date-fns/latest). License and full tree-shaking/timezone claims from the homepage could not be confirmed by fetch (site returned only a title in the excerpt) — **UNVERIFIED**: date-fns's IANA timezone support requires the companion `@date-fns/tz` package as of v4 in prior general knowledge, but this specific claim was not confirmed against a fetched primary source in this session and should be re-verified before relying on it.
- **dayjs**: `dayjs@1.11.23`, MIT license, zero deps, smaller bundle (3.06kb gzip vs date-fns 17.5kb gzip per bundlephobia, though see the tree-shaking caveat below) — [registry](https://registry.npmjs.org/dayjs/latest), [bundlephobia dayjs](https://bundlephobia.com/api/size?package=dayjs@1.11.23), [bundlephobia date-fns](https://bundlephobia.com/api/size?package=date-fns@4.4.0).
- **Bundlephobia caveat**: bundlephobia's date-fns number (70.7kb min / 17.5kb gzip) is for the _entire_ package; date-fns is designed for per-function named-import tree-shaking (e.g. `import { format } from 'date-fns'`), so real bundle cost is much smaller when only a few functions are used — flagging this the same way as the zod bundlephobia caveat, since it wasn't independently re-confirmed against date-fns's own docs in this session (fetch returned only a title).
- **Temporal API**: confirmed **not available** as a Node global — Node 26's own globals reference page lists all current globals (AbortController, fetch, WebSocket, URLPattern, etc.) and Temporal is absent — [nodejs.org/api/globals](https://nodejs.org/api/globals.html). MDN confirms Temporal is "Limited availability... not Baseline because it does not work in some of the most widely-used browsers," i.e., not shipped in all major browsers, and recommends `@js-temporal/polyfill` or `temporal-polyfill` until then — [MDN Temporal](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal). **Do not build on native Temporal** for either Node 26 or the browser without a polyfill.
- **What we actually need**: per Cube's own REST API docs, Cube parses relative date strings itself via the Chrono library server-side — `"dateRange": "last 30 days"` (or `"last week"`, `"today"`, `"from 7 days ago to now"`, etc.) is sent as-is and Cube resolves it, including for the single-string form of date filter `values` — [Cube query-format docs](https://docs.cube.dev/reference/core-data-apis/rest-api/query-format). This directly confirms the task's premise: **wechart does not need to compute "last 30 days" into fixed dates itself for AC-083** — it only needs to (a) offer a picker of relative-preset strings that match Cube's accepted vocabulary, and (b) _display_ the resolved dates/labels back to the user, which is a much lighter date-handling need (formatting a `Date`/ISO string in the user's locale/timezone) than full range arithmetic.
- **Recommendation**: given Cube itself resolves relative ranges, wechart only needs lightweight date _formatting_ and timezone display (for time-dimension granularity labels and showing what a relative preset currently resolves to), not full range-math. `dayjs` (3kb, zero deps, MIT, plugin-based timezone support) is sufficient for this and is lighter than date-fns's tree-shaken cost; date-fns is preferable only if the team later needs a larger surface of pure functions with stronger type-level immutability guarantees. Recommend `dayjs@1.11.23` for both API and web app, with the `utc`/`timezone` plugins if IANA-zone display is needed — **UNVERIFIED**: dayjs's timezone-plugin correctness/DST edge cases should get a follow-up check before relying on it for anything beyond display formatting.
- **Needed at all?** A minimal formatting need could arguably be met with `Intl.DateTimeFormat` (built into Node 26 and all evergreen browsers) instead of any library, since Cube does the range math. This is worth the team confirming: if wechart's only date need is "format this ISO date/timestamp for display in the user's locale/timezone" and "list relative-preset options as a fixed string enum," `Intl.DateTimeFormat` alone may remove the need for `dayjs`/`date-fns` entirely — flagged as an open question below rather than decided unilaterally, since it changes the stack.

## 5. Number/currency formatting (AC-046)

- Cube's dimension/measure `format` field accepts **named formats** — `number`/`number_N`, `percent`/`percent_N`, `currency`/`currency_N`, `abbr`/`abbr_N` (SI-prefix abbreviation, e.g. K/M/G), `accounting`/`accounting_N`, `id` (raw integer) — **and**, for full control, "any valid d3-format specifier string directly (e.g., `$,.2f`, `.0%`, `.2s`)" — [docs.cube.dev/measures](https://docs.cube.dev/reference/data-modeling/measures), [docs.cube.dev/dimensions](https://docs.cube.dev/reference/data-modeling/dimensions). Time dimensions separately accept POSIX strftime format strings with d3-time-format extensions.
- `Intl.NumberFormat` (built into Node 26 and all evergreen browsers, zero install) covers: `style: 'currency'|'percent'|'unit'|'decimal'`, `notation: 'compact'|'scientific'|'engineering'` (compact ≈ Cube's `abbr`), `currencySign: 'accounting'` (parenthesized negatives — matches Cube's `accounting` format), and `signDisplay` — [MDN Intl.NumberFormat constructor](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/NumberFormat).
- **Gap**: `Intl.NumberFormat` has **no mechanism to interpret an arbitrary d3-format specifier string** (`$,.2f`, `.2s`, etc.) — its options are a fixed enum, not a mini-language parser. Since Cube explicitly allows model authors to set `format` to any raw d3-format string, `Intl.NumberFormat` alone cannot satisfy AC-046 for that case.
- **Recommendation**: use `d3-format@3.1.2` (ISC license — [registry](https://registry.npmjs.org/d3-format/latest)) as the formatter for any Cube member whose `format` is a raw d3-format string or one of the named formats that map 1:1 to d3-format conventions (`abbr`→`~s`, `percent`→`%`, etc.), since it is the same specifier language Cube documents. Reserve `Intl.NumberFormat` only for locale-aware currency symbol/decimal-separator concerns d3-format doesn't handle (d3-format needs an explicit locale object via `d3-format`'s `formatLocale`, whereas `Intl.NumberFormat` derives locale automatically) — this is a design choice for the caller to confirm, not decided here.
- **Needed at all?** `Intl.NumberFormat` is sufficient and library-free for the subset of Cube formats that map onto its enum (`number`, `percent`, `currency`, `accounting`, `abbr`-via-compact) but not for raw d3-format strings, so a small formatting utility (`d3-format` or a hand-written specifier parser) is still required for full AC-046 compliance.

## Gotchas

- Zod v4's error-customization API (`error` param) is a breaking change from v3's `message`/`invalid_type_error`/`required_error`/`errorMap` — any copy-pasted v3-era snippets need updating — [zod.dev/v4](https://zod.dev/v4).
- Bundlephobia numbers for `zod` and (likely) `date-fns` overstate real browser cost because both ship many entry points/functions and rely on tree-shaking; use the library's own bundle-size docs, not raw bundlephobia, for browser-budget decisions — [zod.dev/packages/mini](https://zod.dev/packages/mini).
- `pino-pretty`'s transport breaks `logger.flush()` — don't wire pretty-printing into any code path that calls `flush()` — [pretty.md](https://raw.githubusercontent.com/pinojs/pino/main/docs/pretty.md).
- pino's `redact` wildcard paths cost materially more (~50%) than explicit key paths — prefer listing exact paths (e.g. `req.headers.authorization`, `context.securityContext.*` only if truly needed) over broad wildcards — [redaction.md](https://raw.githubusercontent.com/pinojs/pino/main/docs/redaction.md).
- Never pass user- or Cube-response-controlled objects directly as `child()` binding keys — nest under a fixed namespace, per pino's own security note — [child-loggers.md](https://raw.githubusercontent.com/pinojs/pino/main/docs/child-loggers.md).
- Cube's `CUBEJS_LOG_REDACTION` default flips on `NODE_ENV`/dev-mode, not on an explicit flag wechart controls — wechart's own pino redaction should be wired the same way (env-driven, on by default whenever `NODE_ENV=production`) so the two systems don't disagree about what's safe to log side-by-side in the same request — [env.ts](https://raw.githubusercontent.com/cube-js/cube/master/packages/cubejs-backend-shared/src/env.ts).
- Temporal API must not be used without a polyfill in either Node 26 or the browser target — it is absent from Node 26's globals and not Baseline in browsers as of this research date — [nodejs.org/api/globals](https://nodejs.org/api/globals.html), [MDN Temporal](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal).
- `d3-format` needs an explicit `formatLocale` call for non-US-English grouping/currency symbols; it does not auto-detect the browser locale the way `Intl.NumberFormat` does — this is a design decision (fixed locale vs. per-user locale) that should be confirmed with the caller before implementation.

- date-fns's license and its exact IANA-timezone story (native vs. requires `@date-fns/tz`) were not confirmed against a fetched primary source in this session (the homepage fetch returned only a page title); re-verify before choosing date-fns over dayjs.
- Whether wechart needs a date library at all, or whether `Intl.DateTimeFormat` alone suffices, given Cube resolves relative ranges server-side — this is a scope question for the caller, not decided here.
- Locale strategy for `Intl.NumberFormat`/`d3-format` (fixed vs. per-user locale) is undecided and affects which formatting approach is simpler.
- Cube's own REST API row-limit default/maximum (needed to implement AC-172's truncation message) was not resolved from the docs fetched in this session and needs separate research against Cube's core-data-apis docs. _(Already answered in `cube/data-apis.md` and `cube/configuration-deployment.md`: default 10,000 rows, maximum 50,000.)_
