## API surface wechart will use

### The base identity

- **Stored.** The table is `connection_bases (model, name, identity, recorded_at, PRIMARY KEY (model, name))`, created by migration 8 (`store/migrations.ts` L242-261).
- **Recorded.** `identitiesOf` computes every connection's identity. It then calls `recordBases` for those that are `settled` (`runtime/runtime.ts` L2439-2451).
  - `recordBases` sends only names this process has no base for. It learns what the store holds (L2456-2467).
  - The store inserts with `ON CONFLICT (model, name) DO NOTHING`. It then reads back in a second statement, "so the read sees a base another instance committed" (`store/revisions.ts` L717-734).
- **When.** `identitiesOf` runs at the start of every `sync` (L2410), every `activate` (L2706) and every poll (`followConnections`, L2485-2494). That is before `servedRevision` builds anything (L2712).
  - A new or changed connection reaches `sync` through `onChanged`. That is called for any stored connection after a change (`connections.ts` L520-522; `runtime.ts` L535-536).
  - So a new connection's base is its identity at the first sync after it is stored.
  - `sync` returns before `identitiesOf` for a model with no head (L2385-2396). Such a model records its bases at its first activation.
- **Which record wins.** The first insert wins. There is no `UPDATE` or `DELETE` of `connection_bases` anywhere (`git grep connection_bases 2d5ac86f24 -- xcube`).
  - The store test runs 8 concurrent first records through one pool. All get one base, later records don't replace it, and each connection has its own (`store.test.ts` L233-245).
- **All instances agree.** The database decides. Each process caches what it read, and a row never changes (`runtime.ts` L2453-2467).
  - Instances on older images don't read the table. `bc18f82c01` aliases every cube on a connection, and `e53cf2a8b8` aliases none. So during a rolling upgrade, mixed instances serve the same epoch under different names.
- **Dropped connection or model.** The base is kept (store test L246-250, which deletes the connection and then the model's row).
  - A connection stored again under the same name at another target is served as moved.
  - At the same target, it is at base again.
- **The key-holder corner.** `settled` is false when a key-holder secret (`credentials`, `oauthToken`, `token`) has no revision and didn't open (`connections.ts` L178-183; `aliases.ts` L8-9, L29-32).
  - Such a connection records no base. `movedIdentities` treats "no base" as moved, so its cubes are aliased (`runtime.ts` L2469-2479).
  - The `unopened` result is cached per `<model>/<name>/<version>/<field>` on that instance (`connections.ts` L158-170). So it stays unopened there until the connection's version changes or the process restarts.
  - **This doesn't apply to wechart.** wechart sends a revision for every sealed field (`packages/api/src/repos/data-sources.ts` L336; `xcube/connections.ts` L296-303). With a revision, `settled` is true whether or not the secret opens.

### What a revision is served as

- `residentsOf` passes `withIdentityAliases` only the identities of connections moved from their base (`runtime.ts` L2629-2635, L2475-2479).
  - A cube on a connection at its base is served exactly as published. That covers its publish-time alias, or an authored `sql_alias`, or none for a root cube.
  - The tests compare the served file byte for byte (`connections.test.ts` L644-649, L700-703).
- A module's app id gains `:c<salt>` only when it holds a moved cube (L2636-2662). At base it is the app id it always had.
- **The epoch still hashes every connection's identity**, moved or not (`servedRevision` L2595-2597; `aliases.ts` L55-58). So any change of target still gives the whole model a new orchestrator, `<base>_<model>_<epoch>` (`config.ts` L177-179).
- **Moved.** The connection's cubes take `sql_alias: x<hash of name@source@identity>`, as at `bc18f82c01` (`aliases.ts` L84-92; unchanged but for its docblock).
- **Moved back.** They have their published names, SQL and rollup table names again (`connections.test.ts` L664-669, L719-722).
  - If every other connection is as before too, the epoch hash is the one before the move. So the orchestrator id is also the one before the move.
- **Moved again to the same target.** The cubes get the same alias as the first time (L730-733).
- A password change keeps the identity, so it keeps the names and swaps the driver (L651-654).

### Overlays

- A preview's revision is served over `base.identities`, the published connections' identities (`runtime.ts` L1382-1387). Its cubes are therefore named as in the revision it is applied over.
- The overlay's own connections go only into `overlayConnectionSets` (L1389-1393). They never reach `identitiesOf` or `recordBases`.
- Cubes on the overlay's own connections, and changed items, have their rollups stripped (L1471-1484).
- Previews that bring connections run on `<base>_<model>_O_<id>_<version>_<epoch>` (`config.ts` L168-172).
- **The guard fix (`dabd7bde6e`).** `overlayConnectionsOf` now matches `overlayOrchestrators` keys by the prefix `<model>/<id>/<version>/` (`runtime.ts` L1758-1763). Those keys are written as `<key>/<epoch>` (`config.ts` L171).
  - The trailing `/` keeps version `1` from matching `10`.
  - No test covers the guard.

### The 503 for a connection that is changing

- `Connections.CHANGING` is `'changed to new settings on this instance; try again'` (`connections.ts` L185-186).
- It is thrown as `Connection "<name>" changed to new settings on this instance; try again` in three places:
  - a compile of another identity (L413-417);
  - a connection changed while it connected (L426-431);
  - a connection newer than the served epoch (`server.ts` L121-125).
- Cube hands it back as `{ error: e.message… }` with `400` (orchestrator errors), or as `{ error: e.toString() }` with `500`. The second begins with `Error: ` (Cube `gateway.ts` L2553-2560, L2578-2587).
- xcube overrides `resToResultFn`. Any answer with status ≥ 400 whose `error` includes that text goes out as `503` with `Retry-After: 2`, and the body is unchanged (`gateway.ts` L120-134).
  - Every Cube HTTP route answers through `resToResultFn` (Cube `gateway.ts` L384-689).
  - So does xcube's introspection (`gateway.ts` L600-621).
- The unit test sends both a 400 and a 500 carrying the text. It expects `{ status: 503, headers: { 'Retry-After': '2' }, body }`, and expects any other error unchanged (`gateway.test.ts` L479-490).
- **The pinned-epoch 503 is unchanged.** Its text is "The connection settings this request was pinned to changed; try again" (`runtime.ts` L817-821). `xcube-bc18f82c01.md` records it as having no `Retry-After`.
- **wechart matches both** (command output: node, running the file's regex on the strings):
  - `Connection "default" changed to new settings on this instance; try again` → true
  - `Error: Connection "default" changed to new settings on this instance; try again` → true
  - `The connection settings this request was pinned to changed; try again` → true
- wechart asks again up to 3 times. It waits `min(Retry-After, 5)` seconds, or 2 s when there is no header (`client.ts` L59, L380-383). Every Cube call goes through that loop (`#send`, L269, L298, L334).
- The README doesn't document this 503. It mentions only the pinned-epoch one (README L481).

### `PUT …/snapshot` with items

- `importItemsSnapshot` turns the snapshot into a changeset (`runtime.ts` L3276-3291).
  - Deletes are every published item not sent (`snapshotChanges`, L3298-3310).
  - Upserts are those new, changed, sent into a folder the tree lacks, or bound to a dropped item.
- `publish` checks the folder of upserts only (`names/publish.ts` L345-351). Before `8d08fac20c` it checked `[...upserts, ...deletes]`. That check dates from slice 3a (`36aedeb6c4`, per `git log -S`). It began to bite once `7f933fb526` sent snapshots as changesets. `7f933fb526` is in `4754c2c960` but not in `e53cf2a8b8`.
- The store replaces the folder tree against the new item set, in the same transaction as the revision (`store/revisions.ts` L938-939, L767-786). So dropped folders go with their items.
- `items.test.ts` L323-339 covers it:
  - A root-only snapshot with a root-only tree answers `201`.
  - Only root items are left afterwards.
  - `PUT …/folders` can add a folder again.
  - A sent item in a folder the tree lacks answers `422` with `{ folderId, kind: 'folder' }`.
- README L914-916 says the same.
- **Also by reading:** an overlay may now delete an item in a folder the tree lacks. Overlay deletes are lenient, so an absent item is ignored (`runtime.ts` L1506-1514).

### Migration 8 and the store

- `migrate` runs at start under an advisory lock, one transaction per migration (`store/migrate.ts` L39-54, L116-131).
- `XCUBE_MIGRATE` defaults to `true` (README L165), and wechart sets none. With `false`, a pending migration stops the start (`migrate.ts` L109-114).
- `minReader: 2`, so `e53cf2a8b8` and `bc18f82c01` (schema 7) still run on a schema at 8. They log "the schema has migrations newer than this xcube; running on" (`migrate.ts` L95-107). Rolling back is therefore possible.
- The table is never pruned. Every connection name ever served keeps a row. wechart's e2e adds one per run-unique data source, such as `changed-in-place.spec.ts`'s `${RUN}_src`.

### Other epochs' rollup tables (Cube's clean-up)

- After each build, Cube's `dropOrphanedTables` lists every table in the model's schema (`PreAggregationLoader.ts` L1089-1156). That schema is named by the model alone (`config.ts` L181-190).
  - With `dropPreAggregationsWithoutTouch` on and `refreshEndReached` set, it keeps only tables this orchestrator used or touched, plus the table just built (L1135-1144).
  - Otherwise it keeps the newest table of each name (L1107-1116, L1141-1143).
- `CUBEJS_DROP_PRE_AGG_WITHOUT_TOUCH` defaults to `true` (`env.ts` L835-837). The touch timeout is 86400 s (L821-823). wechart's own research records the same (`cube/pre-aggregations.md` L497-498; `cube/per-folder-models.md` L251).
- The used, touched and refresh-end records are keyed under the orchestrator's cache prefix (`PreAggregations.ts` L362-380; `QueryCache.ts` L266-268). That prefix is the orchestrator id (`QueryOrchestrator.ts` L103-104).
- The refresh worker sets refresh-end at the end of each full cycle (`RefreshScheduler.ts` L691-692). It touches each table it finds current (`PreAggregationLoader.ts` L221-243).
- xcube's guard stops only a *superseded* epoch from dropping tables (`server.ts` L59-80).
- **So, by reading, in wechart's deployments:**
  - The current epoch drops other epochs' tables at its first build after its first full refresh cycle. That covers identity-named tables of earlier moves and base-named tables while the connection is moved.
  - A connection moved back to its base after that finds its tables gone and rebuilds them once.
  - Nothing is dropped before the new orchestrator's first full cycle, because no refresh-end record exists for it yet.
- An API instance with an external refresh worker serves the newest table of the same *structure* version at once (`PreAggregationLoader.ts` L160-187). Where a base table survives, it serves at once.

### Upgrading from `e53cf2a8b8` (the Helm release)

1. Migration 8 runs at the first start.
2. Each connection's identity at its model's first activation is its base, so no cube is aliased at serve time (`runtime.ts` L2635).
3. Rollups: same names and the same SQL give the same structure version. So, by reading, the existing tables serve and nothing rebuilds. This is not tested, and was not run.
4. The orchestrator id goes from `<base>_<model>` (`e53cf2a8b8` `config.ts` L170) to `<base>_<model>_<epoch>` (`config.ts` L177). So Cube's result cache, queues and rollup bookkeeping start empty once for every model with connections, and each distinct query reads its source once.
5. At each model's next publish, `4754c2c960`'s due items are re-aliased (the table in `xcube-4754c2c960.md`, "Folder views' `sql_alias`, and the upgrade").
   - At `bc18f82c01` this changed nothing served for cubes on stored connections. Now, at base, it does.
   - wechart's seed model has no due item.
6. **The caveat is right.** A connection changed in place while `e53cf2a8b8` served still has tables under its published names built from the earlier target. At `2d5ac86f24` its base is its current identity, so those tables serve until their refresh keys renew.
7. Upgrading the worker first isn't needed by reading, since both images use the same names.
   - Changing a target mid-roll is unsafe. An `e53cf2a8b8` worker would build base-named tables from the new target.

### Upgrading from `c561077b94` … `8d08fac20c` (compose)

- The epoch hash is unchanged. `identityOf` and `epochOf` only gained a docblock and `settled` in this range. So the orchestrator id stays the same.
- Cubes on stored connections go back to their published names. By reading, the published-name tables are probably gone (see the clean-up above), and they rebuild once. Rollup-served queries answer "not built yet" until the worker builds them.
- The identity-named tables the older image built stay in that orchestrator's touched set until their records expire (24 h). They are dropped at a later build.

## Gotchas for wechart

1. **A connection's first identity is special for as long as the name exists.**
   - A data source edited in xcube after its first sync, even before any cube uses it, is "moved": its cubes serve under `x<hash>` aliases.
   - The same holds for a data source deleted and made again under the same name at another target.
   - For the Helm-seeded root `default`, the first re-targeting (for example, from the sample database to the real warehouse) aliases every root cube for good. That is R38's rule (`docs/spec.md` AC-328).
2. **A BigQuery key, Snowflake OAuth token or Dremio token entered again, even the same one, moves the connection off its base for good.**
   - wechart mints a revision per envelope (`xcube-bc18f82c01.md`, Gotcha 6), and a new revision never equals the base's.
   - Its cubes stay aliased, and their rollups rebuild once.
3. **Moving back to base restores names, not necessarily tables.** With Cube's default clean-up, base tables are dropped once the moved epoch has finished a refresh cycle and built a table. Back at base, rollup-served tiles answer "not built yet" until rebuilt (a `400`; `loadTile` doesn't retry it).
4. **The upgrade from `e53cf2a8b8` still re-reads every query once** (the new orchestrator ids). At the next publish it may re-alias `4754c2c960`'s due items. Don't change a connection's target during a rolling upgrade.
5. **Compose (from `bc18f82c01`) rebuilds its rollups once.** The chart and compose give Cube and its worker one image value, so they upgrade together and there is a "not built yet" window.
6. **A whole snapshot is now authoritative for folders too.** A snapshot whose tree omits a folder deletes that folder's items rather than refusing. wechart builds the tree from its own store, so this is what the reset case needs.
7. **The new 503 covers every Cube route**, introspection included. Its body can start with `Error: ` (the 500 path). wechart's regex isn't anchored, so it matches both.
8. **Still true from `xcube-bc18f82c01.md`:**
   - Gotcha 1: the pinned-epoch 503 has no `Retry-After`. wechart defaults to 2 s.
   - Gotcha 3: no revision claim covers a connection change. Wait for cube-state `live`.
   - Gotcha 10: a failed epoch compile shows only in `GET …/revision`'s `instance`.
   - Gotcha 11: two orchestrators per model during the grace.
9. **Older 503s that say "try again" are still not in `CATCHING_UP`.** They predate this range:
   - "The overlay this request was pinned to is no longer compiled here; try again" (`runtime.ts` L815, L1762);
   - "Cube is busy compiling; try again" (L2002, L2018);
   - `Model "<m>" kept changing while connection "<n>" was removed; try again` (L1909).
10. **`connection_bases` only grows.** Each run-unique data source in e2e adds a row that is never removed.
