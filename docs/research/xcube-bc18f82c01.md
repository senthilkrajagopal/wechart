## API surface wechart will use

### A connection's identity

- `identityOf` (`aliases.ts` L43-53) hashes `[driver, authMethod, fields, named]`.
  - `fields` are sorted by key and leave out `ssl`, `sslRejectUnauthorized`, `sslCa`, `sslCert`, `encrypt` and `trustServerCertificate` (L11-12, L47-49).
  - `named` lists each sealed field that is `credentials`, `oauthToken` or `token` (L8-9, L29-32).
  - Each named secret counts by the revision wechart sent for it. Without a revision, it counts by the first 12 hex digits of the SHA-256 of the opened secret. A secret that can't be opened counts as `unopened` (`connections.ts` L154-176; `aliases.ts` L51).
- Nothing else that is sealed counts, such as `password`, `sslKey`, `privateKey`, `privateKeyPass` or `clientSecret`. A new value for the same user keeps the identity.
- The unit tests (`test/unit/connections.test.ts`) cover this:
  - L188-193: field order, a sealed password and TLS fields don't change the identity; a new database or auth method does.
  - L194-197: a service-account key with the same revision keeps the identity, and another revision changes it.
  - L115-133: with no revision, the same key sealed again keeps the identity, and another key changes it.
- In wechart's forms, the identity-bearing secrets are BigQuery's `credentials` (`packages/core/src/data-sources/drivers.ts` L179), Snowflake's `oauthToken` (L159) and Dremio's `token` (L268).
- wechart sends `revisions` on every `PUT …/connections/{name}` (`packages/api/src/xcube/connections.ts` L296-303). It mints a new revision for each envelope it stores (`repos/data-sources.ts` L572-590). A save stores only the secrets entered again (`sealed = change.sealed ?? {}`, L471).

### Epochs: the served key, aliases and orchestrators

- **Served key.** `servedKeyOf` is `xcube:<model>:<revision>:<hash12>~<epoch12>`, or the plain app id for a model with no connections (`runtime.ts` L170-184). `epochOfKey` reads the epoch back (L187-189).
- **Serve-time aliases.** `withIdentityAliases` (`aliases.ts` L92-166) walks each YAML `cubes:` entry.
  - A cube's data source is its own `data_source`, else its parent's through `extends`, else `default` (L117-128).
  - A cube whose data source is a stored connection gets `sql_alias: x<…>`. The alias is 5 to 9 base-32 characters of SHA-256 of `<name>@<data source>@<identity>` (L78-82, L136), sized so `<alias>_<rollup>` fits `MAX_TABLE_STEM` (25, `names/publish.ts` L21) where it can.
  - A clash lengthens the alias by 2 characters at a time, up to 12, in name order (L141-149).
  - **An authored `sql_alias` on such a cube is replaced** (L150-151). The unit test asserts this (L212).
  - Views are left alone, as are files that aren't `.yml`/`.yaml`, hold several documents or don't parse (L100-110, L153-160).
- **Modules.** A module's app id gains `:c<hash of its files' salts>` (`runtime.ts` L2600-2604, L2610-2622). A module with no cube on a changed connection keeps its app id and stays compiled. `activate` compiles only residents that aren't compiled yet (L2692-2693).
- **Orchestrators.**
  - `contextToOrchestratorId` gives `<base>_<model>_<epoch>` for a model with connections (`config.ts` L160-180).
  - An overlay preview's is `<base>_<model>_O_<id>_<version>_<epoch>` (L168-172; `connections.test.ts` L473).
  - The epoch is read off the request's pin (`runtime.ts` L2470-2479).
- **Drivers.**
  - `resolveDriver` gives a data source only the driver of its context's epoch identity (`server.ts` L121-126).
  - `driverFor` refuses a stored connection of another identity, both before and after connecting (`connections.ts` L406-410, L419-424).
- **Rollup clean-up.** An orchestrator of a superseded epoch drops no table (`server.ts` L59-91). Epochs share the model's rollup schema (README L501-504).
- **Retirement.** A replaced revision is kept for `XCUBE_RETIRE_GRACE_MS`, 300000 by default (README L168). Once no kept revision is served over an epoch, its orchestrators and drivers are released (`runtime.ts` L2873-2884).

### A change of identity, step by step

1. **Heard.** The instance that answers the PUT calls `connections.changed` (`runtime.ts` L1842). Other instances hear by notification (L2203). A missed notification is found by the poll: `refreshSecurity` → `connections.refresh` → `followConnections` (L1129-1132, L2298, L2450-2459). The poll runs every `XCUBE_POLL_INTERVAL_MS` (60000), or `XCUBE_POLL_INTERVAL_DOWN_MS` (10000) while notifications are down (`settings.ts` L166-167; `runtime.ts` L2272).
2. **Same identity (a new password).** Each live driver is rebuilt, tested and swapped (`connections.ts` L493-510). A failure keeps the old driver and reports `failed`.
3. **Another identity.** There is no swap. `onChanged` runs `sync` (`connections.ts` L513-515; `runtime.ts` L536). `sync` computes the new key and activates the head over it (L2407-2413): it compiles the changed modules, switches, and retires the old revision.
4. **Probed.** After the switch, each connection whose identity changed is probed: it is connected with a pool of one, released, and reported `live` or `failed` under the stored version (`runtime.ts` L2422-2427; `connections.ts` L522-534).
5. **Removed.** `onChanged` isn't called for a removed connection (`connections.ts` L513), so its epoch change is picked up at the next poll.

### `GET …/revision`

- The route is `admin/routes.ts` L346-352, which calls `runtime.status` (`runtime.ts` L2922-2934).
- It answers `{ model, generation, mode, current: { revision, contentHash, itemsHash, files, bytes, createdAt, source } | null, modules?: [{ id, version, cubes, copies }], instance: { revision, state, error? } }` (`store/revisions.ts` L33-39; README L936-949, L252-253). That shape is unchanged in the range.
- `instance` describes only the process that answers.
- `state: 'failed'` with `error` means the current head, or its re-key over new settings, didn't compile (`runtime.ts` L2909-2914). The failure is recorded under the served key (L2709-2713). It is retried after 30 s, 2 min and 8 min, then every 10 min (L2749-2766).
- While an epoch switch is compiling, `state` stays `active`, because it compares the head and not the epoch (L2915-2917).
- wechart's `revision()` reads only `generation`, `mode` and `current` (`packages/api/src/xcube/client.ts` L231-248).

### Connection health after a change

- The shape is unchanged: `{ name, version, revisions, instances: [{ instance, version, state, error, reportedAt, current }] }` (README L801-812).
- After a change of identity, every instance that switches reports the new version through its probe. Before this range, only instances holding a driver reported.
- The heartbeat re-writes a report only while its instance holds a live driver for the connection (`connections.ts` L365-375). A probe's report on an instance that runs no query through the connection ages out within the hour.
- wechart's `cubeStateOf` (`xcube/cube-state.ts` L30-43) shows `waiting` until each instance reporting within the hour reports the new version. It then shows `live`, or `failed` if any current report failed.

## Gotchas for wechart

1. **The new 503 isn't retried by wechart's server.**
   - `CATCHING_UP` in `packages/api/src/cube/client.ts` L48-49 doesn't match "The connection settings this request was pinned to changed; try again". The API returns it as `503 { error, source: 'cube' }` (`server.ts` L2506-2513).
   - Tiles ask again on a 503 for up to 90 s (`packages/web/src/query/loadTile.ts` L22-35). `/api/sql`, `/api/acceleration`, the meta reads and the jobs calls don't.
   - It is rare: it needs a request still in flight when the old revision's grace ends (5 min by default).
2. **"…changed to new settings on this instance; try again" is a Cube error, not a 503.** Neither wechart's client nor the tiles retry it.
   - It comes from an instance that has heard of a new identity but not yet switched, for a data source whose driver the old epoch hasn't built.
   - By reading, it can also answer introspection of a connection added moments before. Introspection reads through the request's orchestrator (`gateway.ts` L666; `server.ts` L182-201), and a connection newer than the served epoch has no identity there (`server.ts` L121-124).
3. **No revision claim covers a connection change.** `wechartRevision` waits for a revision number (README L95-100), and an epoch switch has none.
   - The AC-161 e2e that wechart promised in its 0400 ask must wait for cube-state `live` before it queries. xcube's own test waits for health in the same way (`connections.test.ts` L625-631).
   - Without that wait, the e2e can read the old target.
4. **Rollup-served tiles fail after a change of target** with Cube's "No pre-aggregation partitions were built yet…" (400) until the worker builds the new table. `loadTile` doesn't retry a 400. After the upgrade, every rollup on a stored connection does this once.
5. **Every data source added, removed, renamed or re-targeted gives the whole model a new orchestrator.** Its result cache starts empty and every data source reconnects.
   - Unchanged cubes keep their aliases, so their rollup table names stay the same.
   - Whether the new orchestrator uses those tables without rebuilding them is UNVERIFIED.
6. **Entering a BigQuery key, a Snowflake OAuth token or a Dremio token again makes a new identity, even when the value is the same.** wechart mints a new revision per stored envelope (Gotcha source above), and each re-entry rebuilds that connection's rollups. Entering a password, client key or private key again doesn't.
7. **Cubes on stored connections show `x<hash>` aliases in their SQL and rollup table names.**
   - `/api/sql` shows these aliases.
   - `/api/acceleration` matches by `preAggregationId` (`server.ts` L880-888), so it is unaffected.
   - `e2e/items-switch.spec.ts` L299 expects `monthly_orders` in a rollup table name. That holds while its model, `e2e-items-switch-<project>` (L213), has no connections.
8. **An authored `sql_alias` on a cube on a stored connection never reaches Cube.** wechart's model editor offers `sql_alias` (`e2e/model-design.spec.ts` L684).
9. **`/api/acceleration` fails when Cube answers its `/v1/sql` call with a 403.** With security on, a query into an unreached folder now gets that 403. The route's `cube.sql` call (`server.ts` L879) is outside its `try`; only the dry run is inside.
10. **An epoch that fails to compile is invisible to wechart today.** Only `GET …/revision`'s `instance` shows it, and wechart doesn't read that field.
11. **A switch keeps two orchestrators per model until the grace ends.** Cube keeps at most 100 (README L499). With one model, this is no concern.
